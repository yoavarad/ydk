### Patterns
- The release path is now: `ydk release` (529) creates `release/vX.Y.Z`, runs `cz bump --yes`, checks for exactly one commit touching pyproject.toml/uv.lock/CHANGELOG.md, pushes and opens the PR. On merge, `release.yml` (530) tags and publishes the GitHub Release with the changelog section for that version (`.github/scripts/changelog_section.py`).
- 528 made the bump self-contained: a pre-bump hook runs `uv lock` and stages `uv.lock`, a CHANGELOG.md is generated per release, and a post-bump hook deletes the tag because cz has no no-tag option (tagging moved to CI on merge).
- Skills ship inside the wheel (`ydk/_skills`, 531). `ydk skills sync [--dry-run]` copies skills and agents to the Claude config dir, writes `.ydk-version` stamps, prunes previously synced files, and respects `CLAUDE_CONFIG_DIR`. `ydk skills status` and a doctor "Skill versions" check warn on stamp drift.
- `ydk upgrade [--version X.Y.Z]` (532) runs `uv tool upgrade ydk` (or a pinned git install), then runs `ydk skills sync` with the uv-tool binary in a new process so the new version's bundled skills are the ones synced. Editable installs are refused.
- Tests fake only the subprocess boundary (`subprocess.run`, uv) and use a tmp config dir through an autouse fixture, in line with the no-internal-mocks rule. A wheel-contents test guards the bundled skills.
- Design choices were checked against cz source rather than assumed: hook order (pre_bump_hooks run after version_files) is why `uv lock` sees the new version.
- Full suite on the later PRs: 3563 passed on 529 and 3626 passed on 532. `tests/catalog/test_go_http_service.py` hangs locally and was ignored on 528 and 529.

### Template suggestions
- PR bodies that only say "Task NNN" (528, 530, 533) carry no summary of the change. The body generator should pull the task description, or the author should write a Summary.
- Add a "Known limitations" line to the PR template; 529, 531 and 532 each used it well.

### Rule suggestions
- When a CLI command spawns a newer version of itself, run the follow-up step in a new process using the installed binary (as 532 does), not the running one.
- Anything that removes a hook-created artifact (the tag in 528) needs a test that proves it is gone (`test_branch_bump_does_not_leave_a_tag`).

### Summary
Epic 525 added a one-command release flow (`ydk release`, commitizen changelog and lockfile sync, CI auto-tag and GitHub Release on merge of a bump) and keeps the installed CLI and Claude skills in step with it (`ydk skills sync/status`, `ydk upgrade`, doctor check), documented in ci-cd.mdx. Main risks carried forward: the Windows locked-exe case in `ydk upgrade` has guidance only, and the CHANGELOG bootstrap covers only tags reachable from v1.6.0.
