Epic 638 ("Task lifecycle hardening (ydk 1.8.0 field findings)") collected fixes for problems found while running `orchestrate-ready-tasks` in consumer repos on ydk 1.8.0. Issue #634 (found in extractor-tester) held three bugs: `task quick` ignored `--base` and switched the main checkout (642), `task start` branched from HEAD while the stored PR base was the default branch (640), and `task done` never committed so PRs were empty while `done` reported success (641). Issue #643 reported that the verification cache replayed a stale FAIL after a line-ending-only fix (645) and suggested not replaying failures (646). Issue #647, from eml-extractor, reported retro files colliding after an issue-number reset (649). Issue #656 reported that `task sync-issues --dry-run` printed `retired: #N`, which misled an agent into thinking a dry run had closed an issue (657). Merged 2026-11-01 between ~05:32 and ~21:27 UTC; 645, 641, 646, 649, 640 and 642 landed within about 90 minutes in the morning, 657 later in the day.

## AI Analysis
No AI analysis available. No Anthropic API key exists, so `ydk memory retrospective --epic 638` could not run. The sections below were written by hand from the task bodies, issue comments and merged PR bodies.

### Patterns
- Four of the seven tasks fixed a mismatch between what a command reported and what it did: `task done` reported success with nothing pushed (641), `--base` was accepted but only recorded (642), the branch point disagreed with the stored PR base (640), and the dry run printed the same line as a real run (657).
- Two tasks (645, 646) came from one cache problem, split into a key fix (hash raw on-disk bytes of files listed by `git ls-files -m`) and a policy fix (cache and replay only PASS results). Replaying a stale FAIL blocks `git push` and `task done`, which pushes agents toward `--no-verify`.
- 649 was a cross-repo identity bug: retros keyed by epic number alone. Retro files now carry `epic_id`/`title`/`url` front-matter, a legacy file without front-matter still matches by name, and a clashing number writes to `<id>-<title-slug>.md`. This very file uses that format.
- 642 and 645 show review at work: 645's reviewer finding (`ls-files -m` misses filtered CRLF) was refuted empirically, with a regression test red before the fix and green after, and a vacuous test was dropped. 642's reviewer findings were left unfixed and recorded as known follow-ups.
- Tests for git behaviour used real temp repos (and a bare origin for 640/641), with `gh` mocked only at the boundary.

### Template suggestions
- PR bodies for 640, 641, 642, 646, 649, 657 are "Task N" plus a truncated verification block, with no Summary text or Test Plan. 645 has the better shape: behaviour summary, console block with counts, review notes, `Closes #N`.
- A task whose review leaves non-blocking findings should file them as tasks, not only as an issue comment (see 642 below).

### Rule suggestions
- A command that accepts a flag must act on it or reject it; recording a value without using it (`--base` in 642) is a bug.
- Git subprocess calls whose failure leaves state behind must have their return code checked (the unchecked `git checkout -b` in 642 and `git branch` in 640).
- Dry-run output must be worded differently from real-run output, in text and JSON.
- A cache key must hash what the checker actually reads, not git's normalized view; failures should not be replayed.
- Anything keyed by an issue or epic number must also carry a second identity field (title, url) since numbers can restart.

### Summary
Epic 638 made the task lifecycle behave as it reports: `task start` and `task quick` branch from the PR base, `task quick` uses an isolated worktree instead of moving the main checkout, `task done` refuses to open an empty PR, the verification cache no longer misses line-ending-only edits or replays failures, epic retros are matched by identity rather than number, and `sync-issues --dry-run` no longer claims to have retired issues. Main carried-forward risk: the four known 642 follow-ups below are unfixed.
