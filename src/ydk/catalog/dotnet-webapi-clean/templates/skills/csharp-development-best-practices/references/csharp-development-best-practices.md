# C# / .NET Engineering Best Practices
## Consolidated development playbook

**Purpose:** A practical rulebook for building and maintaining reliable C#/.NET projects. It is the knowledge source for the `csharp-development-best-practices` agent skill (`SKILL.md` in the parent directory).

**Scope:** This is a working engineering standard, not a claim that every rule is appropriate in every architecture. Document deliberate deviations and explain why.

**Authorship and license:** Written by the YDK owner (yoavarad) and vendored into this repository by the YDK `dotnet-webapi-clean` ignition pack. Released under the MIT License.

## 1. How to apply this playbook

Treat these as engineering rules, not as an article to read once.

- Before implementing an unfamiliar area, consult the relevant section.
- Before opening a pull request (PR), run the checklist in Section 16.
- During review, refer to a rule or section instead of repeating the full explanation.
- If a rule is deliberately not followed, add a short comment or design note explaining the reason.
- If a production incident or repeated review comment reveals a missing rule, propose an update through a reviewed change to this document.
- Prefer rules backed by a real failure mode. Keep the “why” visible so the rule can be applied sensibly to cases not explicitly covered here.

The step-by-step agent workflow (inspect, plan, implement, verify, report) lives in `SKILL.md`; see Section 19.

### 1.1 Defaults for repositories generated by `dotnet-webapi-clean`

Repositories scaffolded by the YDK `dotnet-webapi-clean` pack start from these defaults. Treat them as the established conventions referred to throughout this playbook:

- **Target framework:** `net8.0` (LTS), set once in `Directory.Build.props`. `net10.0` is a supported opt-in: change that `TargetFramework` line and bump the version-pinned 8.x Microsoft packages (EF Core, `Microsoft.AspNetCore.Mvc.Testing`) to the matching major version. Do not multi-target by default; it doubles the build/test matrix and requires both SDKs locally.
- **Layering:** Domain / Application / Infrastructure / Api. Domain has no framework dependencies; Application depends only on Domain.
- **HTTP surface:** ASP.NET Core Minimal APIs. Endpoint delegates stay thin and call Application-layer services; business logic does not live in endpoint code.
- **Persistence:** EF Core with the SQLite provider, so `dotnet build` and `dotnet test` need no live database. Other providers (for example PostgreSQL) are a deliberate swap in Infrastructure.
- **Repository pattern:** each repository interface is declared in the Application layer and implemented with EF Core in Infrastructure. Application services depend on the interface, and tests substitute in-memory fake repositories.
- **Error contract:** service methods return `null` for an expected "not found" outcome and generated endpoints translate that into `Results.NotFound()`. Unexpected exceptions propagate. When adding a central error path, use ASP.NET Core `ProblemDetails` (`AddProblemDetails()` with `UseExceptionHandler()`) as described in Section 2.7.
- **Tests:** xUnit, with service tests against fake repositories and endpoint tests through the in-process test host.

The generated scaffold is a starting point, not a finished example of every rule. Its service and repository signatures do not yet take a `CancellationToken`, its endpoints bind generated request records but return domain entities directly instead of dedicated response DTOs, and it does not register a central `ProblemDetails` exception handler. When you implement or extend that code, bring it in line with Sections 2.7, 4.2, and 6.1 rather than copying those gaps.

## 2. Error handling and exceptions

### 2.1 Never swallow an exception

**Rule:** Every `catch` block must handle the failure meaningfully, add useful context and rethrow, or intentionally ignore it with a documented reason.

An empty or comment-only catch turns a visible failure into silent data loss or inconsistent state.

```csharp
// Avoid
try
{
    await repository.SaveAsync(order, cancellationToken);
}
catch (Exception)
{
    // Ignore
}

// Prefer: catch only when this layer can make a meaningful decision.
try
{
    await repository.SaveAsync(order, cancellationToken);
}
catch (DbUpdateConcurrencyException ex)
{
    throw new OrderConflictException(order.Id, ex);
}
```

### 2.2 Catch only exceptions you can handle

**Rule:** Catch the narrowest exception type that this layer can actually handle. Let unexpected failures propagate to the application's central exception handler.

Do not catch `Exception` merely to return `null`, return a generic failure, or continue as if the operation succeeded. Broad catches can hide programming errors and cancellation.

### 2.3 Preserve stack traces and causes

**Rule:** Use `throw;` to rethrow the current exception. When wrapping it in a domain/application exception, pass the original exception as the inner exception.

```csharp
catch (IOException ex)
{
    throw new ImportFailedException($"Could not read file '{fileName}'.", ex);
}
```

Do not use `throw ex;` and do not create a new exception containing only `ex.Message`; both discard useful diagnostic information.

### 2.4 Log an unhandled failure once, at the boundary

**Rule:** Do not log an exception at every layer and then rethrow it. Log unexpected failures at the boundary that owns the response, normally the global exception handler.

Repeated log-and-throw produces duplicate stack traces and noisy alerts. Lower layers should add context when wrapping an exception, but should not emit duplicate error logs unless they are handling the failure there.

### 2.5 Do not use exceptions as normal control flow

**Rule:** Represent expected outcomes—such as not found, invalid user input, or a failed parse—with normal return values or result types. In this pack, a nullable return is the default for "not found" (Section 1.1); the `Result` type below is illustrative, so use one only if the repository already has it.

```csharp
var user = users.FirstOrDefault(u => u.Email == email);
if (user is null)
{
    return Result.NotFound($"No user with email '{email}'.");
}
```

Use `TryParse` rather than exceptions for routine parsing of untrusted data.

### 2.6 Fail fast with guard clauses

**Rule:** Validate method preconditions near the top of the method and keep the happy path shallow.

```csharp
ArgumentNullException.ThrowIfNull(order);

if (order.Customer is null)
    throw new ArgumentException("Order must have a customer.", nameof(order));

if (order.Items.Count == 0)
    throw new ArgumentException("Order must contain at least one item.", nameof(order));

// Main operation follows with minimal nesting.
```

Distinguish programmer errors from environmental failures. Fail fast for invalid state and invalid startup configuration; handle transient network or dependency failures with an explicit, bounded recovery strategy where appropriate.

### 2.7 Use one consistent global error response

For ASP.NET Core APIs:
- Configure one central exception-handling path rather than writing repetitive `try/catch` blocks in every endpoint.
- Return a consistent, machine-readable error format, preferably `ProblemDetails`.
- Never return stack traces, secrets, SQL details, or internal exception messages to clients.
- Include a trace/correlation identifier so support staff can connect a client-visible failure to server logs.
- Choose HTTP status codes consistently: `201` for created resources, `202` for accepted asynchronous work, `204` for successful no-content responses, `400` for malformed input, `401` for unauthenticated requests, `403` for forbidden requests, `404` for missing resources, `409` for conflicts, and `500` for unexpected server failures. Choose a consistent policy for validation errors (`400` or `422`).

## 3. Logging and observability

### 3.1 Use structured logging

**Rule:** Pass values as named message-template parameters. Do not use string concatenation or interpolation for normal `ILogger` messages.

```csharp
// Avoid
_logger.LogInformation($"Order {order.Id} shipped to {city}");

// Prefer
_logger.LogInformation(
    "Order shipped: {OrderId} to {City}",
    order.Id,
    city);
```

Named fields make logs searchable and avoid formatting messages unnecessarily when a log level is disabled.

### 3.2 Choose log levels deliberately

- **Error:** An operation failed and requires attention or investigation.
- **Warning:** Something went wrong, but the system recovered or is operating in a degraded mode.
- **Information:** A significant business event or operation boundary, such as an order being created or an import completing.
- **Debug:** Diagnostic detail useful during investigation.
- **Trace:** Very fine-grained details; generally too noisy for normal production operation.

Ordinary user mistakes, such as an invalid email address or a rejected password, are not automatically errors. Avoid treating every event as `Information` or `Error`.

### 3.3 Never log secrets or sensitive data

Do not log passwords, access tokens, API keys, authorization headers, full payment-card data, national identifiers, health data, or raw request bodies that may contain sensitive fields.

Avoid logging whole request objects. A field may become sensitive in a future change without anyone noticing that an existing log statement now exposes it. Log only the specific safe identifiers and metadata needed for diagnosis.

### 3.4 Make requests traceable

Propagate a correlation/trace ID through request processing and outbound calls. In .NET, use logging scopes and/or the platform's tracing facilities so that logs from multiple classes can be associated with the same request. Put the ID in the log context rather than manually adding it to every message.

### 3.5 Avoid logging inside hot loops

Do not emit an `Information` log for every row in a large import or every item in a high-volume loop. Log operation boundaries and aggregate counts, durations, and failure totals. Use per-item diagnostic logging only when needed and at an appropriate level.

## 4. Async, cancellation, timeouts, and concurrency

### 4.1 Keep asynchronous code asynchronous

**Rule:** Never block on asynchronous work using `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()` in normal application flow. Use `await` and make the call chain asynchronous up to the framework entry point.

```csharp
public async Task<Order> GetOrderAsync(int id, CancellationToken ct)
{
    return await _service.GetOrderAsync(id, ct);
}
```

A synchronous boundary that cannot be changed should be isolated, documented, and not spread through the codebase.

### 4.2 Pass cancellation tokens end to end

**Rule:** Async methods that perform I/O should accept a `CancellationToken` and pass it to downstream operations that support cancellation.

```csharp
public async Task<Order?> GetAsync(int id, CancellationToken ct)
{
    return await _db.Orders
        .FirstOrDefaultAsync(order => order.Id == id, ct);
}
```

Do not accept a token at the endpoint and silently drop it in the service or repository. Cancellation prevents abandoned requests from consuming resources unnecessarily.

### 4.3 Set explicit timeouts for outbound calls

Every outbound HTTP or other remote dependency call must have a deliberate timeout appropriate to the operation. Do not rely on unbounded waits or accidental library defaults. Configure connection/request timeouts centrally and ensure retry policies cannot extend total latency without a bound.

### 4.4 Do not use `async void` except for event handlers

Use `Task` or `Task<T>` for asynchronous methods so callers can await completion and observe failures. `async void` is reserved for event-handler signatures that require it.

### 4.5 Do not fire-and-forget background work

**Rule:** Do not launch detached tasks whose completion, exceptions, and shutdown behavior are unmanaged.

Prefer a hosted background service and a bounded queue for background work. Ensure the system has an error path, logging, cancellation/shutdown behavior, and an appropriate retry policy. A bare `_ = SomeAsyncOperation()` is not a background-processing design.

### 4.6 Bound parallel work

Parallel operations can reduce latency, but unbounded concurrency can overwhelm a database, remote API, thread pool, or connection pool. Limit concurrency and consider dependency capacity, rate limits, cancellation, partial failure, and ordering requirements.

### 4.7 Protect shared mutable state

Assume a singleton service can be accessed concurrently by many requests. Prefer immutable state. If mutation is necessary, use a suitable concurrent collection, lock, or other explicit synchronization strategy. Ordinary `Dictionary` and `List` instances are not safe for concurrent mutation.

### 4.8 Use `IAsyncEnumerable<T>` for genuine streams

When data should be processed incrementally, prefer streaming (`IAsyncEnumerable<T>`) over loading an unbounded result set into a `List<T>`. Streaming does not replace pagination where the API contract requires page navigation and a bounded page size.

### 4.9 `ConfigureAwait(false)` in libraries

For reusable library code that should not resume on a captured synchronization context, follow the library's established `ConfigureAwait(false)` convention. Do not apply it mechanically to every ASP.NET Core application method; first follow the repository's platform and library conventions.

## 5. Nullability, validation, and domain modeling

### 5.1 Enable nullable reference types

Use nullable reference types (`<Nullable>enable</Nullable>`) and treat warnings as meaningful. Do not silence warnings with `!` unless the invariant has been established and the reason is clear. A null-forgiving operator is not a substitute for understanding the data flow.

### 5.2 Validate untrusted data at boundaries

Validate data where it enters the process: HTTP requests, files, queue messages, environment/configuration, and third-party responses. Give useful, specific validation errors at the boundary. Internal domain logic should work with validated values and should not repeatedly revalidate the same external contract at every layer.

Validation at the boundary does not mean trusting data from every internal component blindly; preserve invariants where objects are constructed and at meaningful trust boundaries.

### 5.3 Make invalid states hard to represent

Prefer types that enforce their invariants at construction over mutable objects that can contain invalid combinations.

```csharp
public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(currency);

        if (amount < 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        if (currency.Length != 3)
            throw new ArgumentException("A three-letter currency code is required.", nameof(currency));

        Amount = amount;
        Currency = currency.ToUpperInvariant();
    }
}
```

Adapt invariants to the actual domain. For example, negative money may be valid for refunds or accounting adjustments, so do not impose a universal non-negative rule without checking the business meaning.

### 5.4 Use framework capabilities before inventing replacements

Prefer established framework support for validation, dependency injection, serialization, caching, retry policies, and configuration. Custom infrastructure creates maintenance burden and may miss edge cases already handled by the framework.

## 6. API contracts and data models

### 6.1 Never expose persistence entities directly from an API

Endpoints should accept and return explicit request/response DTOs. Persistence entities should remain behind the service/data-access boundary.

Benefits:
- internal fields cannot leak accidentally;
- clients cannot mass-assign fields they should not control;
- database refactors do not silently alter public contracts;
- serialization does not unexpectedly trigger lazy-loading queries or object cycles.

Where practical, project directly to a DTO in the database query so only required columns are retrieved.

### 6.2 Treat published API contracts as compatibility commitments

Do not rename or remove published JSON fields casually. Add fields compatibly where possible; deprecate and remove old fields only through a documented versioning/deprecation process. Do not assume every client can deploy at the same time as the server.

### 6.3 Use decimal types for money

Use `decimal` in C# for monetary values, not `float` or `double`. Choose suitable fixed-precision database types and explicit rounding rules. Do not assume a particular rounding policy without confirming the business/accounting requirement.

### 6.4 Use consistent error responses and status codes

Follow Section 2.7. Do not return HTTP `200` with a body such as `{ "success": false }` for a failed request. Clients, monitoring, and infrastructure rely on status codes.

## 7. Configuration, dependency injection, and secrets

### 7.1 Keep environment-specific values out of code

Do not hard-code service URLs, credentials, thresholds, retry counts, or other deployment-specific values inside business logic. Put them in configuration, bind them to typed options, and inject those options where needed.

Avoid reading raw `IConfiguration` keys deep inside domain/business logic; that hides dependencies and spreads configuration knowledge.

### 7.2 Never commit secrets

Secrets such as passwords, connection strings containing credentials, API keys, certificates, and tokens belong in environment variables or a dedicated secret store. Commit templates or examples with safe placeholder values only.

If a secret is committed, rotate it first. Removing it in a later commit does not remove it from Git history, clones, caches, or forks.

### 7.3 Validate configuration at startup

Use the Options pattern and validate required configuration before the application begins serving requests.

```csharp
builder.Services
    .AddOptions<OrderOptions>()
    .Bind(builder.Configuration.GetSection("Orders"))
    .ValidateDataAnnotations()
    .ValidateOnStart();
```

A broken deployment should fail during startup rather than fail on the first request that uses a missing setting.

### 7.4 Use dependency injection correctly

- Prefer constructor injection for required dependencies.
- Depend on suitable abstractions when they improve boundaries and testability; do not introduce interfaces mechanically for every class. Repository and Application-service interfaces are deliberate boundaries in this pack (Section 1.1), not mechanical ones.
- Keep service responsibilities and layers clear.
- Match DI lifetimes to dependency lifetimes. A singleton must not capture a scoped service (the captive-dependency problem).
- Do not use service location throughout application logic as a substitute for explicit dependencies.
- Avoid circular dependencies; treat them as a design smell to resolve rather than hide with wiring tricks.

### 7.5 Reuse HTTP clients safely

Do not construct `new HttpClient()` per request, and do not create an unmanaged static client without a deliberate lifetime/DNS strategy. Prefer `IHttpClientFactory` and configured, named/typed clients.

## 8. JSON serialization

### 8.1 Configure serialization once and reuse it

Do not create `JsonSerializerOptions` for every serialization call. Configure shared options centrally, such as in ASP.NET Core startup or a dedicated serialization component.

### 8.2 Be explicit about contract-sensitive behavior

Do not rely on accidental defaults for enum representation, property naming, null handling, date/time representation, or converters when these affect an API or persisted format. Treat serialization settings as part of the contract and cover them with tests.

### 8.3 Prefer one serialization system per boundary

Prefer `System.Text.Json` for standard .NET applications unless there is a clear requirement for Newtonsoft.Json. If Newtonsoft.Json is required, configure and use it consistently. Avoid mixing serializers with different settings and behavior without a deliberate boundary.

### 8.4 Consider cycles and untrusted polymorphic data

Know whether the object graph can contain cycles and whether serialization could trigger lazy loading. Do not enable broad polymorphic deserialization of untrusted input without a security review. Prefer DTOs and explicit allowed types.

## 9. Data access and Entity Framework Core

### 9.1 Prevent N+1 queries

Do not issue a database query inside a loop when the same data can be retrieved in a set-based query. Project or join the required data, or fetch related entities in a deliberate batch.

```csharp
var orders = await _db.Orders
    .Select(o => new OrderSummary(o.Id, o.Customer.Name, o.Total))
    .ToListAsync(ct);
```

Review generated SQL and query counts, not just the apparent simplicity of the LINQ expression.

### 9.2 Paginate collection endpoints and queries

Never return an unbounded collection from an API or load an entire growing table by default. Enforce a maximum page size, use deterministic ordering, and select only required fields. Consider cursor/keyset pagination for very large datasets or deep pages when appropriate.

### 9.3 Parameterize SQL

Never concatenate raw input into SQL. Prefer LINQ/EF Core or parameterized SQL (including Dapper parameters) for raw queries. Parameters protect values; dynamic identifiers such as column names require allow-listing because they generally cannot be parameterized as ordinary values.

### 9.4 Keep transactions short and database-focused

Do not hold a database transaction open while making HTTP calls, uploading files, sending email, waiting on a user, or performing unrelated slow work. Long transactions hold locks and connections and increase contention/deadlock risk. Keep transaction boundaries around the database unit of work and coordinate external side effects separately.

### 9.5 Use `AsNoTracking()` for read-only EF Core queries

When results are only being read and do not need to be updated through the current `DbContext`, use `AsNoTracking()` where appropriate to avoid change-tracking overhead.

### 9.6 Save once per unit of work, not once per row

Avoid calling `SaveChangesAsync` for every item in a batch when the items form one logical unit of work. Batch changes appropriately while keeping transaction size and memory use bounded. Do not create one enormous transaction for an unbounded import.

### 9.7 Understand deferred execution and enumeration

LINQ queries often execute when enumerated, not when declared. Avoid accidentally enumerating a database-backed query multiple times or evaluating it after the intended `DbContext` lifetime. Materialize deliberately when needed and be conscious of the amount of data loaded.

### 9.8 Keep `IQueryable` inside the data-access boundary

Avoid returning `IQueryable<T>` from repositories/services as a way to leak query construction to arbitrary callers. It couples callers to EF Core, makes query execution timing unclear, and can lead to unexpected database access. Prefer methods that return a concrete result or an intentional query abstraction.

### 9.9 Use asynchronous EF Core methods

Use asynchronous EF Core APIs for I/O-bound database work and pass cancellation tokens. Do not wrap synchronous database calls in `Task.Run` to pretend they are asynchronous.

## 10. Resource management and time

### 10.1 Dispose resources deterministically

Use `using` / `await using` for resources that implement `IDisposable` / `IAsyncDisposable`, such as streams and database connections. Do not rely on the garbage collector to release scarce external resources promptly.

### 10.2 Store and transmit UTC instants

Use UTC-based timestamps internally and across service boundaries; convert to a user's chosen time zone only at the presentation edge. In .NET, use `DateTimeOffset` for unambiguous instants where appropriate. Be explicit when a value represents a calendar date or a local wall-clock time rather than an instant.

### 10.3 Inject time-dependent behavior

Use `TimeProvider` (or the repository's established clock abstraction) instead of directly calling the system clock deep inside business logic. This makes expiry, retention, scheduling, and boundary conditions testable without waiting for real time.

## 11. Testing

### 11.1 Test observable behavior, not implementation details

Prefer assertions on returned values, externally visible state changes, emitted messages, or API responses. Avoid tests that primarily assert internal method-call sequences or private implementation details; those make safe refactoring unnecessarily expensive.

### 11.2 Keep expected values independent

Do not calculate the expected result with the same formula or logic used by production code. Use clear, independently reasoned literals or test data so a shared mistake cannot make the test pass.

### 11.3 One behavior per test; use descriptive names

Use Arrange–Act–Assert (in xUnit, `[Fact]` for a single case and `[Theory]` with inline data for a table of cases). Each test should focus on one behavior and have a name that describes the scenario and expected result, for example:

`Create_WithNoItems_ReturnsValidationError`

A failing test name should help explain what broke without requiring the reader to open the test body.

### 11.4 Every bug fix should include a regression test

Write a test that reproduces the bug and fails without the fix. If the bug cannot be reproduced in a test, investigate whether the root cause has actually been understood.

### 11.5 Test the boundaries and failure paths

Cover validation, missing data, dependency failures, cancellation, timeout behavior, serialization contracts, and concurrency-sensitive logic where relevant. Prefer a mix of unit and integration tests appropriate to the risk; do not substitute mocks for testing important framework/database behavior.

## 12. Naming, structure, and maintainability

### 12.1 Name things for the reader

Choose names that communicate domain meaning and intent. Avoid vague names such as `data`, `manager`, `helper`, `process`, or `temp` when a more specific name is possible. Follow the naming conventions already used in the repository.

### 12.2 Delete dead code

Do not leave commented-out code, unused methods, obsolete branches, or abandoned abstractions “just in case.” Version control preserves history. Remove dead code and keep the active code path understandable.

### 12.3 Comments explain why, not what

Prefer code that explains what it does through naming and structure. Add comments for non-obvious constraints, business decisions, workarounds, invariants, and reasons a seemingly simpler option is unsafe. Update or delete comments when behavior changes.

### 12.4 Keep methods focused and at one level of abstraction

A method should have a clear purpose. Extract meaningful operations when that improves readability, but do not split code into many tiny methods with no domain meaning. Avoid mixing orchestration, business rules, transport concerns, and low-level persistence details in one method.

### 12.5 Keep layers and responsibilities clear

Keep endpoints focused on transport concerns, application/services on orchestration and use cases, domain types on business invariants, and data-access components on persistence. Use the architecture already present in the repository unless there is a clear, reviewed reason to change it.

## 13. Security baseline

### 13.1 Treat all external input as untrusted

Validate and normalize data from clients, files, queues, environment configuration, and third-party services. Validation is not a replacement for authorization or safe query construction.

### 13.2 Check authorization and resource ownership

Authentication proves who the caller is; it does not prove the caller is allowed to access a particular record. For every operation on a resource ID, check ownership/tenant boundaries and the caller's permissions. Do not rely on unguessable IDs as authorization.

### 13.3 Do not construct executable content from raw input

Never concatenate untrusted values into SQL, shell commands, filesystem paths, HTML, or other executable/interpreted contexts. Use parameterization, safe APIs, context-appropriate encoding, and allow-lists. Validate file paths against the intended root directory where relevant.

### 13.4 Handle passwords with a purpose-built password hasher

Never store plaintext passwords and do not use reversible encryption as a substitute for password hashing. Use a maintained password-hashing implementation with appropriate salts and work factors; follow the platform's current security guidance.

### 13.5 Keep dependencies maintained

Use supported framework/library versions, monitor security advisories, update vulnerable dependencies, and remove packages that are no longer needed. Treat dependency updates as part of ongoing maintenance rather than a one-time setup task.

## 14. Performance principles

Optimize based on measured bottlenecks, but prevent known structural problems early:

- Avoid N+1 database queries.
- Paginate and bound input, output, queues, retries, and parallel work.
- Select only the columns and rows needed.
- Avoid repeated serialization-option construction and per-call creation of expensive clients.
- Avoid per-row database saves when batching is appropriate.
- Avoid per-item logging in high-volume loops.
- Keep transactions short.
- Stream large datasets when incremental processing is appropriate.
- Measure query count, allocation, latency, and throughput when performance is material; do not assume a simple-looking LINQ expression is efficient.
- Do not introduce caching or complex concurrency before understanding correctness, invalidation, memory bounds, and actual need.

## 15. Tooling and automated enforcement

Use automated checks for rules that can be reliably enforced. Useful examples:

- C# compiler nullable-reference-type warnings.
- CA1031 for catching general exception types.
- CA2200 for rethrowing exceptions in a way that can reset stack details.
- CA2254 for non-constant logging message templates.
- CA2100 for SQL queries that may be vulnerable to injection.
- Sonar rules where available for swallowed exceptions and logging issues.

Recommended repository practice:
- Enable nullable reference types.
- Keep analyzer configuration in the repository and apply it consistently in local development and CI.
- Treat important analyzer/build warnings as errors when the project is ready to do so.
- Run formatting, analyzers, build, unit tests, and relevant integration tests in CI.
- Prefer framework-provided mechanisms over hand-rolled alternatives.
- Verify analyzer IDs and configuration against the target SDK and analyzer package versions before adopting them; this document is not a substitute for checking the actual toolchain.

## 16. Pull request checklist

### Correctness and errors
- [ ] No empty or meaningless `catch` blocks.
- [ ] Caught exceptions are specific and handled at the correct layer.
- [ ] Rethrows preserve stack traces; wrapped exceptions preserve the inner exception.
- [ ] Errors are not logged repeatedly at every layer.
- [ ] Guard clauses keep the main path readable.
- [ ] Expected outcomes are modeled without exceptions as routine control flow.

### Logging and diagnostics
- [ ] Logs use structured placeholders, not interpolation or concatenation.
- [ ] Log levels are deliberate.
- [ ] No secrets, credentials, or unnecessary personal data are logged.
- [ ] Requests can be traced with a correlation/trace ID.
- [ ] No noisy per-item logging in hot loops.

### Async and concurrency
- [ ] No `.Result`, `.Wait()`, or `.GetAwaiter().GetResult()` in normal async flow.
- [ ] Cancellation tokens are passed through.
- [ ] Outbound calls have explicit timeouts.
- [ ] No unmanaged fire-and-forget tasks.
- [ ] Shared mutable state has a concurrency strategy.
- [ ] Parallel work is bounded.

### Contracts and data
- [ ] APIs use DTOs rather than exposing persistence entities.
- [ ] Published contracts remain backward compatible or have a migration plan.
- [ ] Money uses `decimal`.
- [ ] Queries are parameterized.
- [ ] No database query inside a loop where set-based access is possible.
- [ ] Collections are bounded/paginated.
- [ ] Transactions contain short database work, not remote I/O.

### Configuration and resources
- [ ] No environment-specific values or secrets are hard-coded.
- [ ] Configuration is typed and validated at startup.
- [ ] DI lifetimes are correct; no scoped dependency is captured by a singleton.
- [ ] HTTP clients are managed through `IHttpClientFactory` or an explicitly justified alternative.
- [ ] Opened resources are disposed deterministically.
- [ ] Time is handled with UTC/explicit zones and testable clock behavior where relevant.

### Tests and maintainability
- [ ] Tests verify observable behavior and use independent expected values.
- [ ] Test names describe scenario and expectation.
- [ ] Bug fixes include regression tests.
- [ ] Relevant error, boundary, and cancellation paths are covered.
- [ ] No dead/commented-out code remains.
- [ ] Comments explain why rather than restating what.
- [ ] Formatters, analyzers, build, and relevant tests pass—or any limitation is explicitly reported.

## 17. Definition of done

A change is ready for review when:
1. It meets the relevant rules in this playbook or documents a justified deviation.
2. The implementation fits the existing architecture and naming conventions.
3. Tests cover the intended behavior and relevant failure paths.
4. The code builds and applicable automated checks pass.
5. Configuration, secrets, logging, and API compatibility have been considered.
6. The PR description explains the problem, the solution, and any material trade-offs.
7. Known limitations and checks that could not be run are stated honestly.

## 18. Keeping the playbook useful

- Add a rule when a production incident or repeated review comment reveals a recurring failure mode.
- Write each rule as an instruction with a reason and, when useful, a bad/good example.
- Review changes to this playbook like code.
- Keep rules actionable and testable; avoid turning preferences into absolute requirements without a clear reason.
- Record deliberate exceptions and the constraints that justify them.
- Consider short architecture decision records for decisions that affect multiple projects or are difficult to reverse.

## 19. Relationship to the agent skill

This file is the **knowledge source**; `SKILL.md` turns it into an actionable agent workflow. In summary:

1. **Inspect first:** identify the target framework/SDK, solution layout, project conventions, analyzers, tests, architecture, and existing patterns before proposing edits.
2. **Scope the change:** identify which rules apply to the requested task; avoid unrelated refactors.
3. **Plan briefly:** for multi-file or architectural work, outline the files and behaviors to change.
4. **Implement consistently:** use the existing dependency injection, logging, configuration, DTO, data-access, and error-handling conventions.
5. **Test:** add/update behavior-focused tests, including a regression test for bug fixes.
6. **Verify:** run the most relevant formatter, analyzer, build, and test commands available in the repository.
7. **Review against this guide:** check async/cancellation, error handling, security, query behavior, resource lifetime, compatibility, and logging.
8. **Report:** summarize changes, tests/checks run and their outcomes, and any remaining risks or unverified items.
9. **Do not pretend:** if a tool is unavailable or a command fails, report that rather than claiming verification succeeded.

The skill does not blindly rewrite an existing project to match a preferred architecture. It follows the repository's established conventions unless they conflict with a clear safety/correctness rule, and explains any meaningful deviation.
