# CI workflow generation (`ydk ci init`)

**Status:** proposed · **ADR:** [0002](../adrs/0002-ci-workflow-generation.md) · **Remote:** GitHub only

## Problem

YDK enforces its process locally (git hooks, verification plugins, `ydk task done` building the PR body) but a
YDK-managed repo gets **no CI**. `ydk init` writes issue/PR templates and labels, nothing under
`.github/workflows/`. Anything that bypasses local hooks (web edits, `--no-verify`, hand-opened PRs) is never
checked, and post-merge bookkeeping (closing tasks, rolling up stories/epics, retiring linked issues) only happens
when someone remembers to run it. The YDK repo itself has these workflows, hand-written and partly duplicated
(`pr-body-check.yml` is a bash re-implementation of `pr-body-validation/check.py` and can drift from it).

A second, concrete bug: `ydk init`'s `_PR_TEMPLATE` has `## Changes` / `## Verification Proof` / `## Spec refs`, but
`pr-body-validation` requires `## Summary` and `## Test Plan`. Every hand-filled PR from the template fails the check.

## Goals / Non-goals

**Goals**

- One command, `ydk ci init`, that writes a complete, least-privilege GitHub Actions setup for a YDK repo.
- Run by `ydk init` automatically for GitHub remotes; usable standalone to retrofit existing repos (e.g. ole-extractor).
- Process checks run the **same code** as local YDK (installed ydk in CI), not copies.
- A stack-specific CI job for stacks with a template (python, dotnet), a generic fallback otherwise.
- Fix the init PR template so hand-filled PRs pass the PR body check.

**Non-goals (v1)**

- GitLab (or any non-GitHub remote). GitLab support is a separate future epic covering init, hooks, and CI together.
- Release / version-from-tag workflows (YDK's own `release.yml`, `version-from-tag.yml` are not generated).
- Dependabot / Renovate configuration.
- Keeping generated files in sync after the user edits them (no merge/patch; see Overwrite).

## User-facing behavior

```text
ydk ci init [--force]
```

- MUST fail with exit 1 and a clear message if `.ydk/config.yaml` is missing, or if `project.remote` is not `github`.
- Reads `project.stack`, `project.spec_location`, `components.components_path`, `components.schemas_path` from
  `.ydk/config.yaml`, and the running ydk version from `importlib.metadata.version("ydk")`.
- Writes files under `.github/workflows/` (creating the directory). Existing files are **skipped** unless `--force`.
- Also writes/refreshes `.github/PULL_REQUEST_TEMPLATE.md` under the same skip/`--force` rule.
- Prints a summary table, one row per file: path, action (`written` / `overwritten` / `skipped (exists)`), purpose.
  Ends with a hint when anything was skipped: `Re-run with --force to overwrite skipped files.`
- Supports the global `--format json` (via `format_or_echo`) returning `{"written": [...], "skipped": [...]}`.
- Exit 0 whenever it completes, even if every file was skipped.

`ydk init --remote github` MUST call the same implementation after `_install_github_templates()`, with
`force=False` regardless of `init --force` (init's `--force` is about config, not about clobbering workflows), and
include the ydk-ci summary in its output. Non-github remotes do not generate workflows.

New CLI group: `src/ydk/cli/ci_cmd.py` (`ci_app`, registered in `src/ydk/cli/__init__.py` as `ci`). Templates ship as
package data (e.g. `src/ydk/templates/ci/*.yml`) rendered with plain placeholder substitution — no Jinja.

## Generated workflows

Common rules for **every** generated file:

- MUST declare top-level `permissions:` with the minimum set listed below (default `contents: read`).
- PR-triggered workflows MUST use
  `concurrency: { group: "${{ github.workflow }}-${{ github.ref }}", cancel-in-progress: ${{ github.event_name == 'pull_request' }} }`.
- Header comment: `# Generated by ydk ci init v<version>. Re-run 'ydk ci init --force' to regenerate.`
- Steps needing ydk use the install snippet from [Installing ydk in CI](#installing-ydk-in-ci).
- File names are prefixed `ydk-` except the stack job (`ci.yml`, see B1/B2).

### A1 + A2 — `ydk-pr-checks.yml` (Phase 1)

- **Trigger:** `pull_request` (opened, synchronize, reopened). **Permissions:** `contents: read`.
- **Job `branch-name`:** bash check of `github.head_ref` against
  `^(feat|fix|docs|chore|refactor|test|ci|perf|release|task)/[a-z0-9-]+$`, with the same error text as YDK's `ci.yml`.
  The ref is passed via `env:`, never interpolated into the script.
- **Job `commit-messages`:** `actions/checkout@v4` with `fetch-depth: 0`, `astral-sh/setup-uv@v7`, then
  `uvx --from commitizen cz check --rev-range "origin/${BASE_REF}...HEAD"` (`BASE_REF` = `github.base_ref`).
  MUST work in repos with no commitizen config (non-Python repos): cz falls back to `cz_conventional_commits`; if a
  config exists the repo's rules apply. Merge/revert/fixup commits follow cz defaults. commitizen SHOULD be pinned to
  a major version (`commitizen>=4,<5`).

### A3 — `ydk-pr-body.yml` (Phase 1)

- **Trigger:** `pull_request` (opened, edited, synchronize, reopened). **Permissions:** `contents: read`.
- **Job `pr-body`:** checkout (`fetch-depth: 0`), setup-uv, install ydk, write the body to a file via env (no shell
  interpolation): `printf '%s' "$PR_BODY" > "$RUNNER_TEMP/pr-body.md"`, then
  `ydk verify pr-body --body-file "$RUNNER_TEMP/pr-body.md" --base-ref "origin/$BASE_REF"`.

**Required ydk change.** `check.py` reads its body only from the plugin context JSON key `pr_body` (plus
`changed_files` for the screenshot rule). Today only `TaskLifecycle._run_pr_body_validation` injects it; `ydk verify
run` has no way to. Add **`ydk verify pr-body --body-file PATH [--base-ref REF]`** that:

1. Discovers plugins, filters by name `pr-body-validation` (same path as `_run_pr_body_validation`; extract that into
   a shared helper so `task done` and the command call one function).
2. Builds context with `pr_body` = file contents and `changed_files` = `git diff --name-only <base-ref>...HEAD`.
3. Prints the plugin's `output`, emits `::error::` lines for each `FAIL:` detail when `GITHUB_ACTIONS=true`, and
   exits with the plugin's pass/fail.
4. Exits 1 with a message if the plugin is not found (unlike `task done`, where a missing plugin is a no-op).

YDK's own `.github/workflows/pr-body-check.yml` SHOULD switch to `uv run ydk verify pr-body ...` in the same epic,
removing the bash copy.

### A4 + A5 — `ydk-sync.yml` (Phase 2)

- **Trigger:** `push` to the default branch, plus `workflow_dispatch`.
- **Permissions:** `contents: read`, `issues: write`, `pull-requests: read`.
- **Concurrency:** `group: ydk-sync`, `cancel-in-progress: false` (serialize; never drop a sync).
- **Job `sync`:** checkout, setup-uv, install ydk; env `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}`,
  `GH_REPO: ${{ github.repository }}`. Steps in order:
  1. `ydk task sync` — reconcile open/in-review tasks against merged PRs, roll up stories/epics (exists today).
  2. `ydk task sync-issues` — retire linked external issues whose tasks are all closed (new, below).

**Required ydk change (A5).** The retire logic lives only in `skills/gh-issue-to-tasks/scripts/sync_issue_state.py`
(+ `_gh.py`, `retire_issue.py`), which managed repos do not have. Move it into the package (e.g.
`src/ydk/core/linked_issues.py`) and expose **`ydk task sync-issues [--dry-run]`**, output
`retired: #12, #15 | none`, JSON via `--format json`. The skill script becomes a thin wrapper over the package
function (or is deleted and the skill calls the CLI). YDK's own `sync-linked-issues.yml` SHOULD switch to the CLI.

### A6 — `ydk-delete-merged-branch.yml` (Phase 1)

Verbatim copy of YDK's `delete-merged-branch.yml`: trigger `pull_request: [closed]`, `permissions: contents: write`,
guard `merged && same-repo && head != default branch`, `gh api -X DELETE .../git/refs/heads/$BRANCH`, tolerant of
already-deleted/protected branches. No ydk install needed. No concurrency block (one run per closed PR).

### A7 — `ydk-spec-integrity.yml` (Phase 2)

- **Trigger:** `pull_request` with `paths:` = `<spec_location>/**`, `<components_path>/**`, `<schemas_path>/**`
  (values from config at generation time; defaults `docs/specs`, `.ydk/components`, `.ydk/schemas`).
- **Permissions:** `contents: read`. No secrets, no LLM calls.
- **Job `components`:** checkout, setup-uv, install ydk, `ydk component validate`. This already runs schema
  enforcement plus the deterministic Layer A linker (`ComponentLinker.validate_references`: dangling refs, broken
  cross-refs; orphans are warnings) and exits 1 on errors. `ydk spec verify` MUST NOT be used (it requires Anthropic
  credentials for its reviewer phase).
- Known gap: `component validate` hard-codes `docs/specs` as the narratives dir instead of `project.spec_location`;
  fix it in this epic so the workflow and the paths filter agree.

### B1 — stack template `ci.yml` (Phase 1)

Trigger `pull_request` + `push` to default branch + `workflow_dispatch`; `permissions: contents: read`; common
concurrency. Named `ci.yml` on purpose: a repo that already has hand-written CI gets it skipped, not duplicated.

**python** (`python-fastapi`, `python-cli`), modeled on YDK's `ci.yml`. Jobs `lint` and `test`, each: checkout,
`astral-sh/setup-uv@v7` (`enable-cache: true`), `uv sync --locked --all-extras --dev`, then
`lint`: `uv run ruff check .`, `uv run ruff format --check .`, `uv run ty check`;
`test`: `uv run pytest -q --tb=short`. Tools resolve via the project's own dev dependencies and config (no paths
hard-coded to YDK's layout). Requires a committed `uv.lock`; `ydk ci init` MUST warn if it is missing.

**dotnet**, modeled on ole-extractor's `ci.yml`, single job `build-test` on `ubuntu-latest`, `timeout-minutes: 30`,
env `DOTNET_NOLOGO`, `DOTNET_CLI_TELEMETRY_OPTOUT`, `SOLUTION`:

- `actions/setup-dotnet@v4` with `global-json-file: global.json` if `global.json` exists at generation time, else
  `dotnet-version: 8.0.x`.
- `dotnet restore $SOLUTION`; `dotnet build $SOLUTION -c Release --no-restore -p:TreatWarningsAsErrors=true`;
  `dotnet format $SOLUTION --verify-no-changes --no-restore`;
  `dotnet test $SOLUTION -c Release --no-build --logger "trx;LogFileName=results.trx" --results-directory TestResults`;
  `actions/upload-artifact@v4` of `TestResults` `if: failure()`.
- Vulnerable package audit: `dotnet list $SOLUTION package --vulnerable --include-transitive`, fail (`::error::`) if
  output matches `\b(High|Critical)\b`.
- `SOLUTION` is the single `*.sln`/`*.slnx` found at the repo root (then one level down) at generation time. If
  zero or several are found, emit `SOLUTION: ""` (dotnet then uses the working-dir project) and print a warning
  telling the user to set it. Repo-specific extras (submodules, OS matrix, extra projects) are the user's to add.

### B2 — fallback `ci.yml` (Phase 1)

For `project.stack` in {`""`, `nextjs-fsd`, `terraform`} or any unknown value. One job `verify`: checkout
(`fetch-depth: 0`), setup-uv, install ydk,
`ydk verify run --trigger git:pre-push --skip-plugin ai-code-review --skip-plugin spec-alignment`.
Those two plugins call an LLM and would need provider credentials in CI; CI stays secret-free.

**Required ydk change.** `ydk verify run` has no way to exclude plugins today. Add a repeatable
**`--skip-plugin NAME`** option (mirroring `ydk task done --skip-plugin`) that drops the named plugins after trigger
filtering and lists them as `skipped` in the output.
**Limitation:** plugins shell out to the stack's toolchain (node, terraform, …) which the runner may lack or have at
the wrong version; plugins that can't find their tool fail open or fail, depending on the plugin. The generated file
MUST carry a comment saying so and pointing to where to add `actions/setup-node` / `hashicorp/setup-terraform`. A real
template for these stacks is follow-up work.

## Stack selection

`project.stack` → template: `python-fastapi`, `python-cli` → B1 python; `dotnet` → B1 dotnet; anything else → B2.
The summary row for `ci.yml` MUST state which one was chosen (`ci.yml — stack CI (python)` / `(fallback: verify run)`).

## Installing ydk in CI

```yaml
env:
  YDK_VERSION: "1.4.1"   # ydk version that generated this file
steps:
  - uses: astral-sh/setup-uv@v7
  - run: uv tool install --python 3.13 "git+https://github.com/yoavarad/ydk@v${YDK_VERSION}"
```

- The version MUST be the running ydk's version at generation time, pinned (no `@main`), in one `YDK_VERSION` env
  per file so upgrading is a one-line edit or a `ydk ci init --force`.
- If the running version is not a release (contains `dev` or a `+local` segment), `ydk ci init` MUST warn that the
  pinned `v<version>` tag may not exist. No network check is made.
- `--python 3.13` because ydk requires 3.13; uv downloads a managed interpreter, so non-Python repos need nothing extra.

## Overwrite / idempotency

- Default: a target file that exists is left byte-for-byte untouched and reported `skipped (exists)`.
- `--force`: every target is (re)written and reported `overwritten` or `written`. No partial merging.
- Running `ydk ci init` twice without `--force` MUST produce zero changes the second time.
- Output is deterministic for a given (config, ydk version, repo files) — no timestamps in generated content.
- Files not in the generated set (e.g. a user's `release.yml`) are never touched, even with `--force`.

## PR template fix

`_PR_TEMPLATE` in `init_cmd.py` MUST contain the sections `pr-body-validation` requires, in `PRBodyBuilder` order:

```text
## Summary

## Verification Results
<!-- Paste command output in a ```console block -->

## Test Plan

Closes #
```

(`Spec refs` is kept as a line under Summary.) A test MUST assert that the template, with a console block filled in,
passes `validate_pr_body`, so template and checker cannot drift again.

## Acceptance criteria

- [ ] `ydk ci init` in a github-remote repo with no `.github/workflows/` writes `ydk-pr-checks.yml`,
      `ydk-pr-body.yml`, `ydk-delete-merged-branch.yml`, `ci.yml` (Phase 1) and, in Phase 2, `ydk-sync.yml`,
      `ydk-spec-integrity.yml`; exit 0; summary lists each as `written`.
- [ ] A second run without `--force` reports all files `skipped (exists)` and changes nothing (mtime + content).
- [ ] With a pre-existing `ci.yml`, it is skipped and all others written; `--force` overwrites it.
- [ ] Non-github remote or missing config → exit 1 with message, nothing written.
- [ ] `ydk init --remote github` produces the same files; `ydk init --remote local` produces none.
- [ ] Every generated file parses as YAML, has a top-level `permissions` block matching this spec, and every
      PR-triggered one has the concurrency block.
- [ ] Every ydk install line pins `v<importlib.metadata.version("ydk")>`.
- [ ] `ci.yml` content: python stacks → uv/ruff/ty/pytest jobs; `dotnet` → setup-dotnet/build/format/test/audit, using
      `global-json-file` iff `global.json` exists and `SOLUTION` set iff exactly one solution found; other stacks →
      `ydk verify run --trigger git:pre-push --skip-plugin ai-code-review --skip-plugin spec-alignment` with the
      toolchain-limitation comment.
- [ ] `ydk verify run --skip-plugin X` excludes plugin X and reports it as skipped.
- [ ] `ydk verify pr-body --body-file f` exits 0 for a `PRBodyBuilder`-built body and 1 (listing missing items) for
      a body lacking `## Summary`; it and `task done` share one validation helper.
- [ ] `cz check` step passes on conventional commits in a repo with no commitizen config (fixture repo test).
- [ ] The new `_PR_TEMPLATE` with a console block passes `validate_pr_body`.
- [ ] Phase 2: `ydk task sync-issues --dry-run` lists issues whose linked tasks are all closed without mutating
      them (gh mocked at the subprocess boundary); `ydk component validate` honors `project.spec_location`.
- [ ] `ci-cd.mdx` reflects the current branch regex, ty path, all workflows, and `ydk ci init`.
