# Memory System

Every time a coding agent completes a task, it generates knowledge. It discovers that a particular library has an undocumented quirk. It decides on an architectural pattern for a specific reason. It tries an approach that fails and switches to another. It learns a naming convention that the project follows. All of this knowledge evaporates when the agent session ends. The next agent working on a related task starts from zero context, likely to rediscover the same quirks, revisit the same failed approaches, and make inconsistent architectural decisions.

YDK's memory system exists to break this cycle. It captures knowledge from completed work, stores it in a searchable index, and retrieves relevant context when new tasks begin. Over time, the system accumulates project-specific knowledge that makes each successive task more efficient -- the compound learning loop that connects Stage 04 back to Stage 01.

## Architecture

The memory system is built on two storage engines working in tandem. ChromaDB provides vector storage with Amazon Bedrock embeddings (Cohere Embed English v3 by default), enabling semantic similarity search -- finding memories that are conceptually related to a query even when they use different words. A BM25 keyword index (JSON-persisted, with k1=1.5 and b=0.75 tuning parameters) provides exact term matching, which is critical for finding memories about specific function names, error codes, or technical terms that vector search often misses.

Content is organized into six ChromaDB collections: `adrs` (architecture decision records), `rules` (project rules and guidelines), `research` (research documents), `specs` (specification files), `tasks` (task files), and `extractions` (knowledge extracted from agent sessions). Each collection is searched independently and results are merged.

## Six Extraction Types

When YDK extracts knowledge from agent session transcripts, it categorizes each memory into one of six types. The categories are not arbitrary -- they have different priority weights because different kinds of knowledge have different values for future tasks:

**Abandoned approaches** (priority 0.9) are arguably the most valuable type of memory. When an agent tries an approach and it fails, recording that failure prevents future agents from wasting time on the same dead end. "We tried using SQLAlchemy async sessions but they deadlock under concurrent writes -- switched to sync sessions with connection pooling" saves the next agent from a multi-hour debugging session.

**Decisions** (priority 0.85) capture architectural choices with their rationale. "Chose event sourcing over CRUD for order state management because the business needs full audit trails and replay capability." Without this memory, a future agent might choose CRUD for a related component, creating an inconsistency.

**Gotchas** (priority 0.8) are traps and edge cases. "The Decimal field in Pydantic v2 requires explicit precision annotation or it defaults to unlimited precision, causing database schema mismatches." These are the things that documentation does not cover but experience teaches.

**Patterns** (priority 0.7) are reusable approaches. "The project uses Protocol-based dependency injection for all core classes, with deterministic fallbacks when no LLM provider is configured." Patterns help agents follow existing conventions rather than inventing new ones.

**Discoveries** (priority 0.6) are facts about how the system works. "The verification cache computes SHA256 hashes of all Python files, not just changed files, because ruff checks can be affected by import resolution from unchanged files."

**Conventions** (priority 0.5) are naming and structural standards. "Test files mirror the source tree: `src/ydk/core/verifier.py` has tests at `tests/core/test_verifier.py`."

## The 4-Factor Scoring Formula

When memories are retrieved, they are ranked by a composite score that balances four factors. The formula is:

```
total = category_weight * 0.50
      + provenance_score * 0.15
      + recency_score * 0.25
      + access_score * 0.10
```

**Category weight (50%)** uses the extraction type priorities listed above. Abandoned approaches score highest because preventing wasted effort is the most valuable thing a memory can do. Conventions score lowest because while useful, they are less critical than avoiding known pitfalls.

**Provenance score (15%)** reflects trust in the memory's origin. A memory stated directly by a user (`user-stated = 1.0`) is more trustworthy than one verified by running tests (`verified = 0.9`), which is more trustworthy than one an agent discovered (`agent-discovered = 0.7`), which is more trustworthy than one extracted by an LLM from a transcript (`llm-extracted = 0.5`). This hierarchy exists because LLM extraction can produce plausible-sounding but incorrect memories.

**Recency score (25%)** uses exponential decay with a 30-day half-life: `0.5 ^ (days / 30)`. A memory created today scores 1.0. A memory from 30 days ago scores 0.5. A memory from 60 days ago scores 0.25. This ensures that recent knowledge -- which is more likely to reflect the current state of the codebase -- ranks higher than stale knowledge.

**Access frequency score (10%)** uses a logarithmic curve: `min(1.0, log2(count + 1) / 10)`. Memories that are frequently accessed by agents are likely to be broadly useful. The logarithmic curve prevents a single heavily-accessed memory from dominating all results.

## Hybrid Search with Reciprocal Rank Fusion

Pure vector search has a well-known weakness: it is excellent at finding semantically similar content but poor at matching specific technical terms. If you search for "SQLAlchemy async session deadlock" and the memory contains "SQLAlchemy async sessions deadlock under concurrent writes", vector search will find it. But if the memory uses the exact error message, keyword search is more reliable.

YDK solves this with hybrid search -- running both vector and BM25 searches, then merging the results using Reciprocal Rank Fusion (RRF) with k=60:

```
rrf_score(doc) = sum(1 / (60 + rank)) for each result list containing doc
```

A document that ranks #1 in both vector and keyword search gets a higher combined score than a document that ranks #1 in only one. Documents that appear in both result lists are boosted. This fusion produces better results than either search method alone because it combines semantic understanding with exact term matching.

Three search modes are available: `vector` (ChromaDB only), `keyword` (BM25 only), and `hybrid` (both with RRF, the default).

## Progressive Retrieval

Not every use case needs the full content of every matching memory. YDK provides three depth levels that control how much content is returned:

**`index`** returns compact entries with a 150-character snippet preview, title, and score. Use this when you need to survey what memories exist without reading them in full.

**`summary`** returns full entries with snippets truncated to 200 characters. Good for browsing and deciding which memories to drill into.

**`full`** returns complete content with no truncation. Use this when the agent needs the full memory content for implementation context.

## Decision Store

Some knowledge is better stored as versioned decisions than as free-form memories. YDK's decision store provides topic-keyed, append-only YAML files at `.ydk/memory/decisions/`. When you record a decision on a topic, YDK auto-increments the version and sets `supersedes` to link to the previous version:

```bash
ydk memory record-decision "authentication-strategy"
ydk memory decision-history "authentication-strategy"
```

This gives you a clear timeline of how architectural decisions evolved, which is invaluable during code review ("why did we switch from JWT to session tokens?") and onboarding ("what is our auth strategy and how did we arrive at it?").

## Contradiction Detection

Knowledge changes over time. An early decision to use library X might be superseded by a switch to library Y. If both memories exist in the system with no connection between them, agents get conflicting guidance.

Contradiction detection is a two-phase process. First, YDK identifies candidates by computing Jaccard similarity on concept tags -- if the new memory and an existing memory share 60% or more of their concepts, they are candidates for contradiction. Second, for each candidate, an LLM evaluates whether the new memory actually contradicts the old one.

When a contradiction is confirmed, the old memory is marked with a `valid_until` timestamp. It is NOT deleted -- this is a deliberate design choice. Deletion would lose the historical record. Instead, the `valid_until` field causes the memory to be filtered from search results by default, while remaining accessible for history queries with `--include-expired`.

## Memory Consolidation

Over time, the same knowledge can be extracted from multiple sessions in slightly different forms. Consolidation finds and merges these duplicates:

```bash
ydk memory consolidate --threshold 0.85 --dry-run
```

The consolidator groups memories by semantic similarity (threshold configurable, default 0.85), keeps the best version (highest provenance, most recent, most accessed), and marks duplicates with `superseded_by` metadata.
