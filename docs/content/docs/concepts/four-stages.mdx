# The SDLC Stages

YDK organizes the entire software development lifecycle into stages, each with its own tools, artifacts, and quality gates. This is not arbitrary structure -- it emerged from evaluating over twenty existing tools and finding that each solved about 60% of the problem with opinions baked in that did not fit. Some tools were excellent at task management but had no concept of specifications. Others handled verification beautifully but assumed you already had a perfect task breakdown. None of them connected the output of one phase as the input to the next in a way that actually worked.

The stages are sequential but not waterfall. You can loop back -- a discovery during execution creates a new task, a failed spec check sends you back to brainstorming, a memory from Stage 04 improves a spec in Stage 01. The stages define *what kind of work* you are doing, not a rigid order that forbids revisiting earlier phases.

```
Brainstorming --> Ignition --> Task Management --> Execution --> Learning
(Stage 01)       (Stage 01.5)  (Stage 02)         (Stage 03)    (Stage 04)
      ^                                                              |
      |______________________________________________________________|
                         compound learning loop
```

## Stage 01: Brainstorming and Design

Stage 01 is human-owned. Coding agents do not participate in brainstorming, and this is a deliberate choice. The brainstorming stage exists because every failed project starts with a vague spec. An LLM given a vague spec will produce vague code, and you will spend more time debugging the ambiguity than you saved. YDK's brainstorming process is designed to be thorough -- by the time you finish, your spec is precise enough that an AI agent can implement from it without asking questions.

The work in Stage 01 centers on writing narrative specifications in markdown, defining component manifests in YAML, and validating the result through both deterministic linking and AI-powered quality evaluation. The narrative tells the story of what you are building and why. The component manifests capture the exact structure -- every entity, every route, every error response, every event, every service interface. The deterministic linker (Layer A) ensures that every reference in your narrative resolves to an actual manifest, and the LLM prose scanner (Layer B) finds things you mentioned in prose but forgot to formalize as components.

The spec checker evaluates 18 criteria across 5 groups (completeness, clarity, architecture, robustness, quality), each scored 1-10 against configurable thresholds. This is not a rubber stamp -- specs routinely fail the first check because they are missing error handling analysis, or their scope boundaries are vague, or they have implementation details leaking into what should be a design document.

For UI-heavy projects, the visual companion provides browser-based design annotation. You push wireframes or prototypes to a Vite dev server, annotate them with selection events, element comments, and rectangle regions, and the feedback is captured as structured data that informs the spec.

Spec evolution is also managed here. When requirements change after the initial spec, you create a change proposal with delta specs that describe what was ADDED, MODIFIED, or REMOVED. YDK can diff the proposed changes against the current spec and archive them once approved, applying the operations to the canonical spec files.

## Stage 01.5: Ignition

Stage 01.5 bridges design and implementation with a single command: `ydk ignite`. Given an installed ignition pack (from the catalog) and validated component manifests, ignition generates a complete runnable skeleton -- domain models, repository interfaces, API routes, test stubs, and migration files. Every piece of business logic that cannot be derived from the manifest is left as a `NotImplementedError` placeholder, registered as a tracked TODO with an `YDK-TODO-NNN` identifier.

The catalog system (`ydk catalog search/install`) provides ignition packs. Each pack declares which component types it consumes and what code it generates. The `hexagonal-architecture` pack, for example, consumes entity, route, error, contract, and external-dep manifests and produces a FastAPI + SQLAlchemy hexagonal layout.

Ignition is idempotent. File content hashes are tracked in `.ydk/ignition-hashes.json`, so re-running `ydk ignite` after adding new components only generates files for the changed manifests. Files where a developer has removed the `GENERATED` header are treated as developer-owned and never overwritten.

The TODO registry created during ignition becomes the backbone of Stage 02 planning. Instead of decomposing the spec into tasks from scratch, you decompose the TODO list -- each TODO maps to a specific business logic implementation that an agent needs to write. This makes tasks smaller, more focused, and directly verifiable: `ydk task done` checks that all assigned TODOs have been resolved.

## Stage 02: Task Management

Stage 02 translates the spec into executable work. With ignition producing the skeleton, tasks now focus exclusively on business logic -- the boilerplate is already generated. The output of this stage is a dependency graph of tasks, each linked to specific TODOs, that agents can pick up and implement independently.

The hierarchy is Epic > Story > Task. Epics map to major features or releases. Stories map to user-visible capabilities. Tasks are the atomic unit -- each one should be completable in a single coding session. After ignition, tasks are linked to `YDK-TODO-NNN` identifiers via `ydk todo assign`, creating a direct mapping between the generated placeholders and the work that needs to be done. This granularity matters because AI coding agents have context windows. A task that requires understanding an entire codebase across multiple sessions will fail. A task scoped to "implement place_order() business logic (YDK-TODO-001)" can succeed in one pass.

Dependency management is the heart of Stage 02. YDK supports 8 dependency types, but only 3 create execution edges in the DAG: `blocks`, `conditional-blocks`, and `waits-for`. The other 5 types (`validates`, `caused-by`, `discovered-from`, `supersedes`, `related`) are tracked for traceability without affecting scheduling. This distinction matters -- a test task that validates an implementation task is a dependency for traceability, but it should not block the implementation.

DAG validation uses Kahn's algorithm to detect cycles, compute parallel execution waves, find the critical path, and measure fan-out. The critical path tells you the minimum project duration even with unlimited agents. The parallel waves tell you how many agents you can productively use. The fan-out identifies bottleneck tasks that should be prioritized.

Complexity scoring sends each task to an LLM for a 1-10 assessment. Tasks scoring 8+ are flagged for decomposition with suggested splits. This catches tasks that are too ambitious before you waste an agent session attempting them.

Resource-constrained scheduling uses greedy topological ordering to assign tasks to available agents. Buffer management tracks schedule health with green/yellow/red zones based on buffer consumption percentages.

## Stage 03: Execution

Stage 03 is where coding agents do the work. The human's role shifts to review and decision-making -- unblocking tasks that hit obstacles, approving PRs, and making architectural decisions when the agent encounters ambiguity.

The execution flow is: start (check dependencies, check gates, create worktree, bootstrap memories) -> plan (post implementation plan) -> implement (write tests first, then code) -> progress (post updates) -> done (run verification, create PR with proof). Each step has guardrails. The TDD guard prevents submitting code without tests. The verification pipeline catches lint violations, type errors, architectural drift, and spec misalignment. The proof system captures actual command output -- not claims, evidence.

Worktree isolation gives each task its own git worktree and branch. This enables genuine parallel execution -- multiple agents working on different tasks simultaneously without stepping on each other's code. When a task is complete, its worktree is merged and cleaned up.

The verification pipeline has 40 built-in plugins across three layers. Layer 1 handles formatting and linting (fast, deterministic). Layer 2 handles architecture and structure (TDD guard, file sizes, import rules). Layer 3 handles AI-powered checks (code review, spec alignment). Layers execute sequentially -- if Layer 1 fails, Layers 2 and 3 are skipped. This saves time and money on LLM calls when basic formatting issues need fixing first.

Gates control external dependencies. A task can require a PR to be merged, a CI pipeline to pass, a timer to elapse, or a human to approve before it can start. Gate conditions are checked automatically (via the `gh` CLI for GitHub, timestamps for timers) except for human gates, which require manual resolution.

## Stage 04: Learning

Stage 04 is what makes YDK different from tools that treat each task as independent. Every completed task generates knowledge -- gotchas, patterns, decisions, abandoned approaches, discoveries, conventions. If that knowledge is not captured and made available for future tasks, each agent starts from zero context. The memory system solves this.

Memory extraction parses Claude Code session transcripts (JSONL format) and uses an LLM to identify six types of knowledge: discoveries (facts about how the system works), decisions (architectural choices with rationale), gotchas (traps and edge cases), patterns (reusable approaches), conventions (naming and structural standards), and abandoned approaches (things tried and rejected, which are arguably the most valuable because they prevent others from wasting time on the same dead ends).

The memories are stored in ChromaDB with Bedrock embeddings and indexed in a BM25 keyword index. Search uses hybrid retrieval with Reciprocal Rank Fusion (RRF, k=60), combining the strengths of vector similarity for semantic matching with keyword matching for exact term lookups. Results are scored using a 4-factor formula: category weight (50%), provenance (15%), recency with 30-day half-life decay (25%), and access frequency (10%).

Contradiction detection prevents stale knowledge from polluting the system. When a new memory contradicts an existing one (detected via concept overlap followed by LLM judgment), the old memory is marked with `valid_until` and filtered from future search results -- but not deleted, preserving the historical record.

The decision store provides topic-keyed, append-only versioned decisions. When an architectural decision changes, the new version automatically supersedes the old one, maintaining a clear history of how the project's design evolved.

<Callout type="info">
The compound learning loop is the key differentiator. Knowledge from Stage 04 flows back to Stage 01 via memory bootstrapping -- when an agent starts a task, YDK searches for relevant memories from past work and includes them in the agent's context. Over time, the system gets smarter about your specific project.
</Callout>
