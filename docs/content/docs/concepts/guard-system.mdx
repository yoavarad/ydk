# Guard System

Guards are real-time enforcement rules that run as Claude Code hooks. They intercept agent actions (file edits, shell commands) and reject violations instantly -- before code is written, not after. This is fundamentally different from verification, which runs after the fact. Guards prevent bad patterns from ever entering the codebase.

## Guard vs Gate

YDK has two layers of enforcement with different performance characteristics and purposes:

| | Guards | Gates (Verification) |
|---|---|---|
| **When** | Instant, on every edit/command | After implementation, on `ydk task done` |
| **Trigger** | `guard:edit`, `guard:command` | `git:pre-commit`, manual |
| **Speed** | Milliseconds (regex/AST) | Seconds to minutes (full suite) |
| **Purpose** | Prevent violations from forming | Catch violations that slipped through |
| **Mechanism** | Claude Code hooks in `.claude/settings.json` | Verification plugins |

Guards are the first line of defense. They catch violations at creation time, saving the expensive verify-fix-verify loop. Gates (verification) are the second line -- thorough but slower.

## Available Guards

YDK ships with six guards:

### `tdd` — TDD State Machine

Enforces the red/green/refactor cycle. The guard tracks the current TDD phase (stored in task frontmatter via `ydk task tdd`) and rejects actions that violate the phase:

- **Red phase**: Only test files can be edited. Implementation changes are rejected.
- **Green phase**: Implementation files can be edited, but only to make failing tests pass. No new features.
- **Refactor phase**: Both test and implementation can be edited, but tests must continue passing.

```bash
# Set TDD phase
ydk task tdd T-a1b2c3d4 --stage red

# Guard rejects implementation edits during red phase
# "BLOCKED: TDD phase is 'red' — only test files may be edited"
```

### `no-noqa` — No Suppression Comments

Rejects any `# noqa`, `# type: ignore`, `// @ts-ignore`, or similar suppression comments. All violations must be fixed, never suppressed.

### `no-mock` — No Mock Usage

Rejects `unittest.mock`, `MagicMock`, `patch()`, and similar mock constructs. YDK projects use real implementations, test doubles, or integration tests -- never mocks.

### `no-manual-pr` — No Manual PR Creation

Prevents agents from running `gh pr create` directly. PRs must be created through `ydk task done`, which attaches verification proof automatically.

### `no-proof-tamper` — No Proof File Editing

Rejects direct edits to `.ydk/proof/` files. Proof must be generated by the verification system, not written by hand.

### `stage-gate` — Stage Transition Enforcement

Ensures stage transitions follow the correct order (01 -> 02 -> 03 -> 04) and that prerequisites are met before advancing.

## How Guards Are Installed

Running `ydk init` installs a single standalone Python script at `.claude/hooks/guard.py` and configures `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit|Bash",
        "hook": ".claude/hooks/guard.py"
      }
    ]
  },
  "permissions": {
    "allow": ["Bash", "Edit", "Write", "Read", "Grep", "Glob"]
  }
}
```

The guard script reads tool context from stdin via `select()` (non-blocking), evaluates all active guards, and exits with code 2 to block the action or code 0 to allow it. The `permissions.allow` entry enables non-interactive use with `--allowedTools` (NOT `--dangerously-skip-permissions`).

## Fail-Open Behavior

Guards fail open -- if stdin is empty, JSON is malformed, or `state.json` is unreadable, the guard allows the action rather than blocking. This ensures that guard infrastructure issues never halt agent progress; the verification layer (gates) catches anything that slips through.

## SubagentStop Hook

In addition to PreToolUse guards, `ydk init` installs a SubagentStop hook that blocks session end if `.ydk/active-task.json` exists. This ensures the agent runs `ydk task done` before a session can terminate, preventing abandoned work without verification proof.

<Callout type="info">
Guards are designed to be fast enough that they do not disrupt the agent's flow. Each guard check completes in milliseconds because they use pattern matching and AST analysis, not full program execution.
</Callout>

## Relationship to Verification

Guards and verification plugins complement each other:

1. **Guards** catch violations in real-time during implementation (Stage 03)
2. **Verification plugins** run the full suite at completion (`ydk task done`)
3. **Spec reviewers** validate narrative quality during design (Stage 01)

A well-guarded project rarely has verification failures because violations are caught at the point of creation. The verification suite then serves as a safety net for anything guards cannot catch (test coverage, architecture rules, AI-powered review).
