# Proof-Based Development

The problem with AI-assisted development is trust. When a coding agent reports "all tests pass" in its chat output, there is no way to verify that claim without running the tests yourself. The agent might have run an outdated test suite. It might have run tests in a different directory. It might have interpreted "no errors" as "all pass" when in fact the test runner did not execute at all. In the worst case, the agent might hallucinate the output entirely.

ODK's answer to this problem is proof-based development: every claim must be backed by a machine-verifiable artifact. Not a summary, not a paraphrase, not a claim -- the actual output from the actual command, captured at the actual time, against the actual codebase.

## What Proof Looks Like

When `odk task done` runs the verification pipeline, each plugin produces a `CheckResult` -- a structured JSON object containing the plugin name, a boolean pass/fail, the raw output from the tool, and the execution duration:

```json
{
  "name": "tests-pytest",
  "passed": true,
  "output": "42 passed in 3.21s",
  "duration_seconds": 3.21
}
```

The `output` field is the key. It is not a summary generated by ODK. It is the actual stdout from running pytest (or ruff, or ty, or whatever tool the plugin wraps). A reviewer reading this output can independently verify the claim -- they can see exactly which tests ran, how long they took, and whether any were skipped or xfailed.

The full `VerificationReport` collects all check results across all layers and is saved as a proof artifact at `.odk/proofs/<task_id>/verification.json`. This file is then embedded in the PR body, creating a permanent record of what was verified and what the results were.

## Why This Matters

Consider the alternative. Without proof, a PR review process looks like this: the agent says "tests pass", the reviewer either trusts that claim or runs the tests locally to verify. If the reviewer trusts and the agent was wrong, bugs ship. If the reviewer re-runs tests, the efficiency gain from using an AI agent is diminished.

With proof, the review process changes fundamentally. The reviewer reads the PR body and sees the actual pytest output showing 42 tests passed. They see the actual ruff output showing zero lint violations. They see the actual type checker output confirming no type errors. They can spot inconsistencies without running anything -- for example, if the PR adds three new functions but the test output only shows 42 tests (the same as before), something is wrong.

Proof also creates an audit trail. Six months later, when someone asks "was this code reviewed?" or "were tests passing when this shipped?", the proof is right there in the PR, timestamped and immutable.

## The Three Verification Layers

ODK organizes its 40 verification plugins into three layers that execute sequentially. If any check in a layer fails, subsequent layers are skipped. This design is intentional -- there is no point running expensive AI code review (Layer 3) if the code does not even pass formatting checks (Layer 1).

**Layer 1: Format and Lint.** These are fast, deterministic checks that catch low-hanging issues in under 5 seconds. The `lint-ruff` plugin runs `ruff format --check` and `ruff check`. The `types-ty` plugin runs the type checker against the configured Python version. The `python-quality` plugin checks for common code quality issues. These checks have near-zero false positive rates -- if they fail, there is a real problem to fix.

**Layer 2: Architecture and Structure.** These checks enforce project conventions and design rules. The `python-tdd-guard` plugin ensures that every staged source file has a corresponding test file -- enforcing TDD at the tooling level, not just as a guideline. The `python-file-length` plugin catches files that have grown too large. Framework-specific plugins check import boundaries (FastAPI adapter isolation, Next.js FSD layers), route organization (route delegation, route splitting), and anti-patterns (no mocks in integration tests, no useEffect for data fetching). These checks take 5-15 seconds.

**Layer 3: AI-Powered.** These checks use LLMs for analysis that cannot be done deterministically. The `ai-code-review` plugin sends the git diff to an LLM for security analysis, code quality assessment, and design review. The `spec-alignment` plugin checks that the implementation matches the spec across six dimensions. These checks take 15-60 seconds and require the `ai` extras. They catch subtle issues -- spec drift, security vulnerabilities, design inconsistencies -- that mechanical checks miss.

## Content-Hash Caching

Running 40 verification plugins on every check would be slow and wasteful when most of your code has not changed. ODK solves this with content-hash caching. Before running a plugin, the verifier computes a SHA256 hash of all Python files in the project. If the hash matches a cached result from a previous run of the same plugin, the cached result is returned instantly.

This means that if you fix a single lint error and re-run verification, only the plugins affected by that file are re-executed. Plugins that check other aspects of the codebase return their cached results in milliseconds.

```bash
# View cache status
odk verify cache

# Clear cache for a specific plugin
odk verify cache --clear-plugin lint-ruff

# Clear all caches
odk verify cache --clear
```

## Auto-Fix and Auto-Repair

Some verification failures have mechanical fixes. The `lint-ruff` plugin supports auto-fix -- when run with `--auto-fix`, it executes `ruff format` and `ruff check --fix` before checking, automatically resolving formatting issues and import sorting problems.

For failures that require more than mechanical fixes, the auto-repair loop provides structured error output designed for coding agents:

```bash
odk verify run --trigger pre-push --auto-fix --repair --max-retries 3
```

The repair loop runs verification, and if it fails, formats the errors as structured JSON:

```json
{
  "all_passed": false,
  "failed_checks": [
    {
      "name": "python-tdd-guard",
      "output": "Missing test file for: src/orders/routes.py",
      "duration_seconds": 0.2
    }
  ]
}
```

This JSON is not meant for humans -- it is meant for the coding agent to parse, understand what needs fixing, and fix it. The loop then re-runs verification, up to `max_retries` times. The key design decision here is that the repair loop does NOT call an LLM itself. It structures errors and lets the coding agent (which already has the full codebase context) decide how to fix them.

## Collapsible PR Body

The PR body assembled by `PRBodyBuilder` uses collapsible `<details>` blocks so reviewers see a clean summary at a glance but can expand any section to inspect raw terminal output. Each verification result gets its own collapsible block, organized into four sections:

- **Deterministic Checks** -- lint, format, and type check results
- **Verification Plugins** -- test output, TDD guard, and other structural checks
- **AI Reviews** -- spec alignment scores and code review findings
- **Screenshots/Videos** -- captured UI proof (when applicable)

This format exists because a flat wall of terminal output is unreadable, but hiding it behind a single summary loses the verifiability that makes proof-based development valuable. The collapsible format gives both: a scannable summary with full evidence one click away.

The agent does not write these sections. `PRBodyBuilder` reads the proof files from `.odk/proofs/<task-id>/` and assembles the body from a deterministic template. The raw output inside each `<details>` block is exactly what the verification command produced.

## PR Commenting

When verification runs in a CI context, `PRCommenter` posts the results as a PR comment using a hidden HTML marker (`<!-- odk-verification -->`) for idempotency. Running verification multiple times updates the same comment rather than flooding the PR with duplicates. The comment includes a table of all checks with pass/fail indicators, the actual output from each check, and the total verification duration.

Proof-based development is not about distrust -- it is about creating a workflow where trust is earned through evidence rather than assumed through claims. The proof artifacts make reviews faster, more reliable, and auditable.
