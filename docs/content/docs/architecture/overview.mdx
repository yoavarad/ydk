# Architecture Overview

ODK follows a strict layered architecture where each layer has clear responsibilities and import rules. This structure was not chosen for aesthetic reasons -- it exists because ODK itself is developed using ODK, and the verification plugins enforce these boundaries. If a core module imports from the CLI layer, the `fastapi-core-purity` style check catches it. If a model imports from a repository, the import isolation check flags it. The architecture is self-enforcing.

## Layer Diagram

```
+-----------------------------------------+
|              CLI Layer                   |
|    (Typer commands, output formatting)   |
+-----------------------------------------+
|              Core Layer                  |
|  (Business logic, no CLI imports)        |
+-----------------------------------------+
|            Models Layer                  |
|     (Pydantic models, strict)            |
+-----------------------------------------+
|          Repository Layer                |
|  (Protocol + 3 backends: local/GH/GL)   |
+-----------------------------------------+
|           Services Layer                 |
|    (Git, Remote, LLM protocols)          |
+-----------------------------------------+
|            Output Layer                  |
|  (Console, Formatters, Live display)     |
+-----------------------------------------+
```

## Import Rules

The import rules are simple and absolute:

- **CLI** imports from Core, Models, and Output. It is the top layer that wires everything together.
- **Core** imports from Models, Services, and Repositories. It never imports from CLI -- this is the boundary that keeps business logic testable without a CLI context.
- **Models** has no internal imports. It is a leaf layer containing only Pydantic models with `ConfigDict(extra="forbid")` for strict validation.
- **Repositories** import from Models only. They implement the protocols defined in the services layer.
- **Services** define protocols and import from Models. They are the interfaces that core depends on.

These rules mean you can test any core module by providing mock implementations of the protocols it depends on, without needing a CLI context, a database, or an LLM.

## Design Philosophy

Six design patterns recur throughout ODK's architecture:

**Protocol-based dependency injection.** Core classes depend on protocols (Python's `typing.Protocol`), not concrete implementations. `TaskLifecycle` depends on `LifecycleTaskRepository`, not `LocalTaskRepository` or `GitHubTaskRepository`. `ComplexityScorer` depends on `LLMProvider`, not a specific Bedrock client. This makes every class independently testable and swappable.

**Deterministic fallbacks.** Every LLM-powered feature has a non-LLM path. When `ComplexityScorer` has no LLM provider, it returns a default score of 5. When `ComponentScanner` has no LLM, it returns an empty result. When `TaskCompactor` has no LLM, it uses deterministic summarization. This means ODK works fully without AI credentials -- the AI features enhance but do not gate the core workflow.

**Repository pattern with factory dispatch.** The factory reads `project.remote` from config and dispatches to the correct backend class. Adding a new backend means implementing the protocol and adding one line to the registry -- no other code changes needed.

**Plugin system by convention.** Verification plugins are discovered by scanning directories for the pattern `<name>/manifest.yaml` + `<name>/check.py`. No registration step, no import magic, no central configuration file listing plugins. Drop a directory with the right files and it is discovered.

**Event system with fire-and-forget.** The `EventBus` emits events on daemon threads. Subscribers receive events asynchronously and cannot block the main flow. This decouples concerns like PR commenting from the task lifecycle without introducing complex async patterns.

**Strict model validation.** All Pydantic models use `ConfigDict(extra="forbid")`, which means any unexpected field in the input causes a validation error. This catches typos, stale data, and schema drift at the boundary rather than deep in business logic.

## Directory Structure

```
src/odk/
  cli/           # 14 command modules + helpers
  core/          # 30+ modules: business logic
  models/        # 18 model modules: Pydantic models
  repositories/  # Protocol definitions + 3 backends
  output/        # Console rendering, formatters, live display
  schemas/       # 13 component type schemas (YAML)
  verifications/ # 40 verification plugins
  templates/     # Scaffolding templates (Jinja2)
  visual/        # Browser overlay assets
  hooks/         # Git hook implementations
```
