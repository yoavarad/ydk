# CI/CD Pipeline

YDK uses three GitHub Actions workflows that enforce the same quality standards in CI that the local verification plugins enforce on the developer's machine. The philosophy is simple: if code passes local verification, it should pass CI, and vice versa. The CI pipeline is not a separate quality gate -- it is the same gate, running in a controlled environment.

## ci.yml: PR and Push Validation

This workflow runs on every pull request and every push to main. It has four jobs:

**Branch name validation** (PRs only) ensures that branch names follow the convention `^(feat|fix|docs|chore|refactor|test|ci|perf|release)/[a-z0-9-]+$`. This is not cosmetic -- the branch naming convention feeds into the conventional commit system, which drives automatic versioning and changelog generation.

**Commit message validation** (PRs only) runs `cz check --rev-range origin/main...HEAD` to validate that every commit follows the conventional commit format. Types are `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ci`, `perf`, and `release`. This validation catches malformed commits before they are merged, preventing versioning confusion.

**Lint** installs all dependencies with `uv sync --locked --all-extras --dev` and runs `ruff check src/ tests/` followed by `ty check src/ --python-version 3.13`. These are the same checks that YDK's Layer 1 verification plugins run locally.

**Test** installs all dependencies and runs `pytest tests/ -q --tb=short -x --ignore=tests/fixtures`. The `-x` flag stops on first failure for fast feedback. The `--ignore=tests/fixtures` flag excludes test fixture files that are not actual test files.

## Versioning: manual `cz bump` + tag-sync

<Callout type="warn">
There is no workflow that auto-bumps the version on merge to main. Version bumps are triggered manually, from a tag pushed on the feature branch, before the PR merges.
</Callout>

The flow:

1. On your feature branch, run `cz bump --yes` (or `cz bump --dry-run` to preview first). Commitizen reads the conventional commits since the last version tag / bump commit and determines the increment: `fix` → patch, `feat` → minor, `BREAKING CHANGE` → major. It updates `version` in `pyproject.toml` and creates a local `vX.Y.Z` tag.
2. `git push origin <branch> --tags` (or `--follow-tags`) pushes both the branch and the new tag.
3. **`version-from-tag.yml`** runs on PR open/sync/reopen. It checks whether a `vX.Y.Z` tag points at the PR's HEAD commit; if so, it rewrites `pyproject.toml:version` to match and commits `chore(release): set version to X from tag vX` back onto the PR branch, so the version bump is visible in the PR diff for review. It only runs for branches in this repository (not forks).
4. **`release.yml`** fires independently, on any `v*` tag push — it doesn't wait for the PR to merge. It creates a GitHub Release with the tag name as the title and auto-generates release notes from the commits since the previous tag.

Because `release.yml` triggers on the tag push itself (step 2), the GitHub Release can go live *before* the PR merges. There is no automatic version management on push-to-main — every bump starts with a manually run `cz bump` on a branch.

## Local Git Hooks

YDK also provides git hooks in `.githooks/` that run the same checks locally before they reach CI:

| Hook | What it does |
|------|-------------|
| `commit-msg` | Validates conventional commit format using `cz check` |
| `pre-commit` | Runs `ruff format` + `ruff check` to catch formatting and lint issues |
| `pre-push` | Validates branch name pattern and runs `pytest` |

Configure the hooks with `git config core.hooksPath .githooks`. The pre-push hook respects YDK's `.verified` flag -- if `ydk task done` ran verification within the last 5 minutes, the pre-push hook skips re-running checks to avoid double verification.
