# Component Schemas

Component schemas define the vocabulary YDK uses to describe your system. Each schema is a YAML file that specifies the fields a component manifest of that type must contain, their data types, whether they are required, validation patterns, and relationships to other components. The schemas live in two locations: built-in schemas ship with YDK at `src/ydk/schemas/`, and project-specific schemas are copied to `.ydk/schemas/` during initialization.

The schema system serves three purposes. First, it enables validation -- when you create or modify a component manifest, YDK checks it against the schema to catch structural errors. Second, it enables scaffolding -- when you run `ydk component create`, YDK reads the schema and generates a template with all fields pre-populated. Third, it enables documentation -- the `ydk docs generate` command reads schemas and produces reference pages listing every field and its constraints.

## How Schemas Work

A schema is a YAML file with a name, description, version, and a map of field definitions:

```yaml
name: entity
description: "A domain model / data object with fields, relationships, and lifecycle"
version: 1
fields:
  id:
    type: string
    required: true
    pattern: "^ydk:entity:.+"
    description: "Unique component identifier"
  description:
    type: text
    required: true
    description: "What this entity represents in the domain"
  fields:
    type: map
    required: true
    description: "All fields on this entity, keyed by field name"
```

Each field definition includes a `type` (string, text, integer, boolean, enum, list, map, ref, ref_list, any), a `required` flag, a `description`, and optional constraints like `pattern` (regex), `values` (enum options), `ref_type` (for cross-component references), `max_length`, `min`, and `max`.

The `ref` and `ref_list` types are special -- they declare that a field references another component. A field with `type: ref` and `ref_type: entity` means the value should be a valid entity component ID. The deterministic linker uses these declarations to validate cross-references between components.

## The 13 Built-in Types

YDK ships with 13 schema types that cover the patterns found in most software systems:

**`entity`** -- Domain models with typed fields, foreign keys, state transition maps, and relationship declarations. The richest schema, designed for database-backed objects.

**`route`** -- API endpoints with HTTP method, path, request/response schemas, authentication, and error references. Works for both REST APIs and CLI commands.

**`error`** -- Error responses with status codes, error code strings, messages, trigger conditions, and recovery suggestions.

**`event`** -- Domain events with typed payloads, producer/consumer declarations, and ordering guarantees.

**`contract`** -- Service interfaces with method signatures, parameter types, return types, and raised errors. Maps to Python Protocols and TypeScript Interfaces.

**`component`** -- UI components with props, framework targets, data sources, and emitted events.

**`page`** -- Frontend pages with routes, layouts, and section compositions.

**`req`** -- Business requirements with rules, acceptance criteria, and priority.

**`ext`** -- External dependencies with endpoints, rate limits, and authentication.

**`hook`** -- Lifecycle hooks with trigger conditions and behaviors.

**`nfr`** -- Non-functional requirements with metrics, targets, and measurement methods.

**`crosscut`** -- Cross-cutting concerns with specifications that apply across the system.

**`test`** -- Test specifications with given/when/then scenario definitions.

## Adding Custom Schemas

You can add project-specific schemas by creating new YAML files in `.ydk/schemas/`. The schema format is the same as the built-in schemas. Once added, the new type is available for `ydk component create` and validation.

See [New Component Schema](/docs/extending/new-component-schema) for a detailed guide.
