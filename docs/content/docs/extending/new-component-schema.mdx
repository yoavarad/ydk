# Creating a Component Schema

The 13 built-in schema types cover common patterns, but your project might have domain-specific component types that do not fit neatly into any existing category. A trading system might need a `strategy` schema type. A healthcare system might need a `regulation` type. A game might need a `level` type. YDK's schema system is extensible -- you can add custom types that participate fully in validation, scaffolding, and documentation.

## Step 1: Design the Schema

Before writing YAML, think about what fields your component type needs. A good schema captures the essential structure of the concept without being so detailed that it becomes a burden to fill in. Ask: if a coding agent reads this manifest, what does it need to know to implement the component correctly?

For example, a `strategy` schema for a trading system might need: a description, the signal type (momentum, mean-reversion, etc.), entry conditions, exit conditions, risk parameters, and data sources.

## Step 2: Write the Schema File

Create `.ydk/schemas/strategy.yaml`:

```yaml
name: strategy
description: "A trading strategy with entry/exit conditions and risk parameters"
version: 1
fields:
  id:
    type: string
    required: true
    pattern: "^ydk:strategy:.+"
    description: "Unique strategy identifier in ydk:strategy:namespace/name format"
  description:
    type: text
    required: true
    description: "What this strategy does and its theoretical basis"
  signal_type:
    type: enum
    values: [momentum, mean-reversion, breakout, statistical-arbitrage, factor-based]
    required: true
    description: "Strategy archetype"
  entry_conditions:
    type: list
    required: true
    description: "Conditions that trigger position entry"
  exit_conditions:
    type: list
    required: true
    description: "Conditions that trigger position exit"
  risk_parameters:
    type: map
    required: true
    description: "Risk management settings keyed by parameter name"
  data_sources:
    type: ref_list
    ref_type: ext
    description: "External data dependencies (market data feeds, etc.)"
  backtest_config:
    type: map
    description: "Default backtesting configuration"
```

The `id` field should always have a pattern that starts with `^ydk:<your-type>:.+` to maintain the component ID convention. Use `ref` and `ref_list` types for fields that reference other components -- this enables the deterministic linker to validate cross-references.

## Step 3: Use the New Type

Once the schema file exists in `.ydk/schemas/`, YDK automatically discovers it:

```bash
# Create a component using the new type
ydk component create strategy trading/momentum-crossover

# List all strategy components
ydk component list --type strategy

# Validate strategy manifests against the schema
ydk component validate
```

The `ydk component create` command reads the schema and generates a template with all fields pre-populated with sensible defaults. You fill in the actual values.

## Step 4: Reference in Specs

Use your custom components in narrative specs just like built-in types:

```markdown
## Momentum Crossover Strategy
Uses 20/50 day moving average crossovers to generate entry signals.
[ydk:strategy:trading/momentum-crossover]
```

The deterministic linker validates these references exactly like built-in types.

<Callout type="info">
Custom schemas are full citizens of the component system -- they participate in validation, scaffolding, reference linking, coverage analysis, and documentation generation, exactly like built-in types.
</Callout>
