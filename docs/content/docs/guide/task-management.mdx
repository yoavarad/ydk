# Task Management (Stage 02)

Stage 02 transforms a validated spec into a plan of attack -- a dependency graph of executable tasks that agents can pick up and implement independently. The quality of this decomposition determines whether execution goes smoothly or devolves into agents stepping on each other's code, implementing features in the wrong order, or attempting tasks that are too large for a single session.

## Creating the Hierarchy

Start with epics for major features, then decompose into stories for user-visible capabilities, then into tasks for atomic implementation units:

```bash
# 1. Create an epic tied to a release
odk task create-epic --title "Orders System" --release "v1.0" --spec-refs orders.md

# 2. Create stories under the epic (with component refs and acceptance criteria)
odk task create-story --title "Place Order" --epic E-abc12345 \
  --spec-refs orders.md --component-refs "odk:entity:orders/Order,odk:route:orders/create" \
  --acceptance "Valid order → 201; Insufficient balance → 422"

# 3. Create tasks under stories with precise descriptions
odk task create --title "Create Order model" --story S-def45678 \
  --component-refs "odk:entity:orders/Order" --spec-refs orders.md \
  --depends-on T-prev1234:blocks --test-strategy "Unit tests for field validation and state transitions"
```

The key to good task decomposition is granularity. A task should be completable in a single coding session -- typically 30-60 minutes of focused agent work. If a task requires understanding multiple subsystems, touching more than 5-6 files, or making design decisions that affect other tasks, it is probably too large and should be split.

### Batch Creation

For creating an entire hierarchy at once, use a batch YAML file with `epics:`, `stories:`, and `tasks:` sections. Each entity has an `id` field for cross-referencing within the file. Task dependencies use placeholder IDs that are resolved to real GitHub issue numbers in a second pass after all issues are created.

```yaml
# batch.yaml
epics:
  - id: E-orders
    title: "Orders System"
    spec_refs: orders.md

stories:
  - id: S-place-order
    title: "Place Order"
    epic: E-orders
    spec_refs: orders.md
    component_refs: "odk:entity:orders/Order,odk:route:orders/create"
    acceptance: "Valid order → 201; Insufficient balance → 422"

tasks:
  - id: T-order-model
    title: "Implement Order model"
    story: S-place-order
    component_refs: "odk:entity:orders/Order"
    depends_on: []
  - id: T-order-route
    title: "Implement POST /orders route"
    story: S-place-order
    depends_on:
      - "T-order-model:blocks"
```

```bash
# Validate without creating issues
odk task create-batch --from batch.yaml --dry-run

# Create everything -- labels auto-created, deps resolved in second pass
odk task create-batch --from batch.yaml
```

Labels (`epic`, `story`, `task`, `blocked-by-code`, `blocked-by-decision`) are auto-created before batch processing. The `--dry-run` flag validates YAML structure, dependency references, component refs, and spec refs without calling the API.

## Assigning TODOs to Tasks

After ignition (Stage 01.5), every `NotImplementedError` placeholder in the generated skeleton is registered as a TODO with an `ODK-TODO-NNN` ID. Link these TODOs to tasks so that completion verification works:

```bash
# See all registered TODOs
odk todo list

# Assign a TODO to a task
odk todo assign ODK-TODO-001 T-abc12345

# Verify all TODOs are assigned
odk todo coverage
```

Tasks should focus on business logic only -- the boilerplate (models, route stubs, repository interfaces, test scaffolding) was already generated by ignition. A single task can have multiple TODOs assigned to it when they are closely related (e.g., both `place_order()` and `cancel_order()` in the same service file).

When `odk task done` runs, it automatically verifies that all TODOs assigned to that task have been resolved -- meaning the `NotImplementedError` has been replaced with real implementation code.

<Callout type="info">
Run `odk todo coverage` before starting a sprint to confirm every TODO is assigned to a task. Unassigned TODOs represent work that will not be tracked or verified.
</Callout>

## Managing Dependencies

Use the `--depends-on` flag with an optional type suffix to declare relationships between tasks:

```bash
--depends-on T-abc12345:blocks        # Must complete first (default)
--depends-on T-abc12345:validates     # Test task, non-blocking
--depends-on T-abc12345:caused-by    # Root cause link, non-blocking
--depends-on T-abc12345:discovered-from  # Found during implementation
```

Only `blocks`, `conditional-blocks`, and `waits-for` affect the execution order. The other types are tracked for traceability -- they help agents understand context without constraining scheduling.

## DAG Validation

Before starting any implementation, validate the dependency graph:

```bash
odk task validate-dag
```

The output shows cycle detection (fatal), parallel execution waves (how many agents you can run), the **critical path (dependency-only)** which is the minimum project duration assuming unlimited agents, and fan-out per task (which tasks are bottlenecks). Self-dependencies are detected and rejected. If cycles are detected, you must restructure dependencies before proceeding.

<Callout type="info">
`validate-dag` shows the **critical path** (dependency-only, ignoring resource limits). `plan-waves` shows the **critical chain** (resource-constrained, accounting for agent availability). These are different: a project with many parallel tasks may have a short critical path but a long critical chain when only a few agents are available.
</Callout>

## Scheduling with Resource Constraints

For teams running multiple agents:

```bash
odk task plan-waves --agents 3
```

The scheduler uses greedy topological ordering: it fills each wave with up to N tasks (N = available agents), completing the wave before starting the next. The output includes per-agent utilization, identifies idle time where agents are waiting for upstream tasks, and shows the **critical chain (resource-constrained)** -- the longest execution path given the available agents.

## Buffer Management

Track schedule health during execution:

```bash
odk task list
# Filter by epic, story, or status (results grouped by status)
odk task list --epic E-orders --status open
odk task list --story S-place-order
odk task list --status in-progress
```

Buffer consumption is categorized into three zones: green (under 33% consumed, on track), yellow (33-66%, watch carefully), and red (over 66%, behind schedule). Early warning from buffer tracking lets you take corrective action -- splitting large tasks, adding agents, or cutting scope -- before delays compound.

## Complexity Analysis

Score all tasks for complexity:

```bash
odk task analyze-complexity
```

Tasks scoring 8+ on the 1-10 scale get flagged with suggested splits. This prevents the common failure mode where a task looks reasonable on paper but turns out to require cross-cutting changes across multiple subsystems. The LLM scorer catches this by analyzing the task's description, dependencies, and spec references.

## Finding Ready Tasks

When agents are available for work:

```bash
odk task ready
```

This lists tasks with all blocking dependencies resolved and all gates satisfied, ranked by fan-out -- the number of downstream tasks each one unblocks. Starting with the highest fan-out tasks maximizes throughput because each completed task unlocks the most new work.

<Callout type="info">
Use `odk task coverage --spec-dir docs/specs` to verify that every spec section has at least one story covering it. Use `odk task component-coverage --strict` to verify every component manifest is referenced by a task. Coverage gaps mean parts of your spec will not be implemented.
</Callout>

## Validation at Creation Time

ODK validates task data at creation time to catch issues early:

- **`--component-refs`** validated against real files in `.odk/components/`
- **`--spec-refs`** validated against real files in the spec directory
- **`--depends-on`** references must point to existing tasks with valid dependency types
- **Self-dependencies** are detected and rejected
- **Acceptance criteria** and **test strategy** trigger warnings if omitted
- **Orphaned tasks/stories** (referencing non-existent parents) are flagged during batch creation

Configure `task_management.coverage_exclude` in `.odk/config.yaml` to skip reference docs (glossary, scope, etc.) from coverage checks.
