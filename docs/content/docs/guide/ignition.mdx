# Ignition (Stage 01.5)

After your spec passes the Stage 01 quality gate, ignition generates a runnable project skeleton from your component manifests. This guide walks through the complete ignition process.

## Prerequisites

Before running ignition, you need:

1. **Validated spec**: Narratives and component manifests from Stage 01, with `odk spec verify` passing
2. **Installed ignition pack**: Run `odk catalog list` to confirm. If none is installed, search and install one:

```bash
odk catalog search "python fastapi"
odk catalog install hexagonal-architecture
```

## Step 1: Preview the Plan

Always preview before generating:

```bash
odk ignite --dry-run
```

This shows every file that will be created, which component manifests drive each file, how many TODOs will be registered, and any components that the pack cannot consume. Review the output carefully -- if the file layout does not match your expectations, you may need a different ignition pack or custom generators.

## Step 2: Generate the Skeleton

```bash
odk ignite
```

Ignition runs generators as subprocesses, one per component type. Each generator reads the relevant component manifests and produces code files with `GENERATED` headers. After generation, three post-checks run automatically:

- **Syntax check**: Verifies every generated Python file parses correctly
- **Circular import detection**: Catches import cycles introduced by the generated code
- **Ruff format**: Ensures all generated code is properly formatted

## Step 3: Verify the Skeleton

Confirm the generated project is actually runnable:

```bash
# Lint passes
ruff check src/ tests/

# Formatting passes
ruff format --check src/ tests/

# Tests can be collected (they will all fail with NotImplementedError)
pytest --collect-only tests/
```

<Callout type="warn">
Do not try to make tests pass at this stage. Every test should fail with `NotImplementedError` -- that is by design. The business logic implementation happens in Stage 03.
</Callout>

## Step 4: Review TODOs

Understand the work that ignition has queued:

```bash
# List all registered TODOs
odk todo list

# See overall coverage
odk todo coverage

# Inspect a specific TODO
odk todo show ODK-TODO-001
```

Each TODO corresponds to a `NotImplementedError` placeholder in the generated code. The TODO ID, file path, line number, and a brief description of what business logic is needed are all captured.

## Step 5: Commit and PR

Create a PR with the generated skeleton:

```bash
git add .
git commit -m "feat: ignition skeleton from hexagonal-architecture"
# Create PR for human review
```

The PR should include all generated files and the TODO registry (`.odk/todos.yaml`). Include the TODO list summary in the PR description so the reviewer understands the scope of remaining work.

## What Happens Next

After the ignition PR is merged:

1. **Stage 02**: Decompose the remaining work into tasks. Use `odk todo assign` to link TODOs to tasks. Tasks are scoped to business logic only -- no boilerplate.
2. **Stage 03**: Agents implement each task by replacing `NotImplementedError` with real code. `odk task done` auto-verifies that all assigned TODOs are resolved.

## Re-Running Ignition

Ignition is idempotent. If you add new component manifests after the initial run:

```bash
# Only generates files for new/changed components
odk ignite

# Force regeneration of everything
odk ignite --force
```

Files where you removed the `GENERATED` header are treated as developer-owned and will not be overwritten, even with `--force`.

## Configuration

```yaml
# .odk/config.yaml
ignition:
  hash_store: .odk/ignition-hashes.json
  post_checks:
    syntax: true
    circular_imports: true
    ruff_format: true
```
