# Spec Evolution

Specifications are living documents. Requirements change, designs evolve, and features get added or removed as the project progresses. Without a structured change management process, spec changes create silent drift -- the canonical spec says one thing, the implementation does another, and no one knows which is correct. ODK manages spec evolution through a structured workflow that tracks changes as explicit proposals with delta specs, reviews, and archiving.

## Proposing a Change

When requirements change, create a change proposal:

```bash
# Minor change (no separate design document needed)
odk change propose add-rate-limiting

# Major change (requires a design document explaining the architectural impact)
odk change propose new-auth-system --mode major
```

This creates a `docs/changes/<name>/` directory with structured artifacts:

- **`proposal.md`** -- What is changing and why. The narrative explanation of the change.
- **`delta-specs/`** -- The actual modifications to existing specs, expressed as ADDED/MODIFIED/REMOVED operations.
- **`tasks.md`** -- Implementation tasks needed to realize the change.
- **`design.md`** -- Only for major changes. The full design document explaining architectural impact.
- **`.change.yaml`** -- Metadata: change name, mode, status, timestamps.

The delta spec format uses markdown with explicit operations:

```markdown
> Target: specs/api.md

## ADDED
### New Endpoint: POST /orders/cancel
Allows users to cancel orders before shipment. Validates that the order
is in a cancellable state (created or confirmed) and transitions it to cancelled.

## MODIFIED
### Endpoint: GET /orders
Updated to support cursor-based pagination with a `cursor` query parameter
instead of offset-based pagination.

## REMOVED
### Endpoint: DELETE /legacy/orders
No longer needed after the migration to the new order system is complete.
```

## Managing Changes

Track active changes through their lifecycle:

```bash
# List all active change proposals
odk change list

# Check status of a specific change (which artifacts exist, what is missing)
odk change status add-rate-limiting

# Preview the diff against the canonical spec
odk change diff add-rate-limiting
```

The diff preview shows exactly how the canonical spec will change if the proposal is archived -- sections that will be added, sections that will be modified, and sections that will be removed.

## Archiving Changes

When a change is approved and implemented:

```bash
odk change archive add-rate-limiting
```

Archiving is the key step. ODK parses the delta specs, applies each operation to the corresponding canonical spec file:

- **ADDED** operations append new sections to the end of the target spec
- **MODIFIED** operations find the matching `###` heading in the target spec and replace its content
- **REMOVED** operations find the matching `###` heading and delete it along with its content

After applying the operations, the change directory is moved to `docs/changes/archive/<date>-<name>/`, preserving the full history of what changed, when, and why.

This archiving process ensures that the canonical specs always reflect the current state of the system, while the archive preserves the change history for auditing and context.
